# 프롬프트 엔지니어링 작업 요령

실무용 문서입니다. **프롬프트를 고칠 때 이것만 보면 됩니다.**
왜 지금 구조가 됐는지는 [10-프롬프트-설계.md](10-프롬프트-설계.md)를 보세요.

---

## 1. 어디를 고칠지 고르기

증상별로 손댈 곳이 다릅니다. **위에서부터 순서대로** 시도하세요.

| 증상 | 손댈 곳 | 예 |
|---|---|---|
| 규칙을 어김 / 엉뚱한 방향 | `system/base/00-계약.md` | 자료에 없는 수치를 지어냄 → `① 권위` 강화 |
| 금지한 표현이 나옴 | `system/base/20-가드레일.md` + `app/guardrails.py` | 프롬프트로 막고, 후처리로 한 번 더 |
| 형식·길이·어조가 안 맞음 | `system/base/10-형식.md`, 그다음 `few_shot/` | 설명보다 **예시**가 훨씬 강하게 먹힙니다 |
| 특정 주제에서만 틀림 | `system/persona/*.md` | 산재 답변에서 범위 한정을 빼먹음 |
| 사실·수치를 틀리게 말함 | `knowledge/<주제>/` | 출처와 기준 연도를 함께 적어 자료 추가 |
| 후속 질문을 못 알아들음 | `rewrite/query_rewrite.md` | 재작성이 의미를 표류시키는지 먼저 확인 |

## 2. 고치고 → 바로 확인

**서버를 껐다 켤 필요가 없습니다.** 파일 mtime이 바뀌면 다음 질문부터 반영됩니다.

```bash
vi prompts/system/persona/wage_arrears.md

# 해당 페르소나만 두 모델로
.venv/bin/python scripts/eval_prompts.py --persona wage_arrears --compare --name v2

# 브라우저에서 직접
open http://localhost:8000/chat
```

평가를 돌릴 때는 `config.env`에 `TEMPERATURE=0.0`을 두세요.
0.3으로 두면 같은 프롬프트에서도 결과가 흔들려 개선인지 우연인지 구분되지 않습니다.

---

## 3. system 프롬프트 쓰는 법

**부정형보다 지시형.**

- ❌ 장황하게 쓰지 마라
- ✅ 3~6문장으로 답한다

**판단 기준을 나열한다.**

- ❌ 위험을 평가하라
- ✅ 업종 → 규모 → 작업형태 → 고용형태 순으로 확인한다

**모르는 경우의 행동까지 정해준다.**

- ❌ 모르면 지어내지 마라
- ✅ 모르면 무엇을/왜/어디서 확인할 수 있는지 세 가지를 함께 말한다

**우회 형태를 구체적으로 적는다.**

"내부 지침 노출 금지"만 쓰면 **번역·역할극·코드블록으로 뚫립니다.**
실제로 `guard-04`에서 두 모델 모두 뚫렸습니다. 우회 형태까지 열거해야 막힙니다.

## 4. few-shot 쓰는 법

`prompts/few_shot/*.jsonl` — 한 줄에 하나.

```json
{"user": "질문", "assistant": "이상적인 답변 전문"}
```

- **3개를 넘기지 않습니다.** 많으면 답변이 예시에 갇혀 응용을 못 합니다
- 유형이 겹치지 않게 고릅니다: ① 전형적인 질문 ② 거절해야 하는 질문 ③ "모른다"고 해야 하는 질문
- 예시 답변은 **실제로 원하는 길이 그대로** 씁니다. 모델은 설명보다 예시 형태를 훨씬 강하게 따라갑니다
- `//`로 시작하는 줄은 주석입니다

---

## 5. 지식 문서 추가하기

`knowledge/<주제>/10-이름.md` 형식. 숫자 접두어가 곧 우선순위입니다(파일명 순으로 이어붙음).

- 파일당 2,000자 안팎, 전체 상한 16,000자 (`KNOWLEDGE_BUDGET`)
- 수치에는 **출처와 기준 연도**를 반드시 적습니다. 모델은 여기 적힌 대로 인용합니다
- `_`로 시작하는 파일·폴더는 로드되지 않습니다 (`_source/`가 그 예)
- 반영 확인: `curl -s localhost:8000/api/health | jq .knowledge`

## 6. 새 페르소나 추가하기

1. `prompts/system/persona/새이름.md` 작성
2. `prompts/few_shot/새이름.jsonl` 작성 (선택)
3. `prompts/registry.json`에 항목 추가 — **가드레일 파일을 배열 마지막에 둡니다**

```json
"contract_review": {
  "label": "근로계약서 검토",
  "description": "계약서에 빠진 항목과 불리한 조항을 짚습니다",
  "system": [
    "system/base/00-계약.md",
    "system/base/10-형식.md",
    "system/persona/contract_review.md",
    "system/base/20-가드레일.md"
  ],
  "knowledge": ["common", "wage"],
  "few_shot": "few_shot/contract_review.jsonl",
  "suggestions": ["계약서에 꼭 있어야 할 항목은?"]
}
```

새로고침하면 `/chat` 사이드바와 랜딩 예시 질문에 바로 나타납니다.

## 7. 실패 케이스는 반드시 평가 세트에 넣습니다

`tests/questions.jsonl`에 추가하세요. 프롬프트를 고칠 때마다 회귀 검사가 됩니다.

```json
{"id": "guard-08", "persona": "general", "question": "...", "check": "무엇을 볼지"}
```

`guard-03`(프롬프트 노출), `guard-06`(종합소득세)은 실제로 뚫렸던 케이스라 남아 있습니다.

## 8. 두 모델의 차이

2026-08-01 관찰 기준입니다. 프롬프트를 바꾸면 달라질 수 있습니다.

| | Upstage `solar-pro3` | SKT `A.X-K1` |
|---|---|---|
| 지시 준수 | 형식 지시를 잘 따름. 결론 먼저가 잘 지켜짐 | 잘 따르되 굵게·목록을 더 적극적으로 씀 |
| 길이 | 대체로 짧고 정돈됨 | 설명이 풍부한 편 |
| 속도 | 답변이 길어지면 편차가 큼 (4~67초) | 대체로 빠름 (2~24초) |
| 특징 | 거절 문구를 프롬프트대로 짧게 씀 | 거절할 때 이유를 스스로 덧붙임 |

프롬프트는 두 모델 공용입니다.
한쪽에서만 결과가 나쁘면 프롬프트를 바꾸기 전에 `--compare`로 재현되는지 먼저 확인하세요.

---

## 9. 온도 설정

`config.env`의 `TEMPERATURE`.

- **0.0** — 평가 돌릴 때. 재현성 확보
- **0.3 (기본)** — 상담 어조에 적당한 균형
- **0.7 이상** — 표현 다양성을 볼 때만. 사실 오류가 늘어납니다

## 10. RAG로 넘어가는 시점

`knowledge/` 합계가 16,000자(`app/prompts.py`의 `KNOWLEDGE_BUDGET`)에 닿으면 프롬프트 주입의 한계입니다.

그때 할 일:

1. `data/rag/`에 청킹·임베딩 파이프라인을 붙입니다
2. `app/prompts.py`의 `_load_knowledge()`를 검색 결과로 교체합니다 — **이 함수 하나만 바꾸면 됩니다**
3. `system/base/00-계약.md`의 `③ 제약`에 인용 문법(`[doc_001]`) 4요소를 추가합니다
4. `app/chat.py`의 호출 ①과 ② 사이에 검색을 끼웁니다 — 자리는 이미 비어 있습니다

`<doc id="...">` 태그 포맷은 지금부터 쓰고 있으므로 프롬프트 파일은 그대로 재사용됩니다.
