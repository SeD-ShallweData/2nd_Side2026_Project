# 평가 방법

작성 2026-08-01 · 구현 [scripts/eval_prompts.py](../scripts/eval_prompts.py), [tests/questions.jsonl](../tests/questions.jsonl)

## 원칙 — 학습노트에서 가져온 것

> 검색기 × 생성기 품질은 **곱셈**입니다. 약한 쪽을 개선해야 이득이 큽니다.
> 프롬프트를 고치기 전에 병목이 검색인지 생성인지 진단해야 합니다.

지금은 RAG가 없으므로 **병목이 100% 생성 쪽**입니다. 검색 지표는 아직 측정하지 않습니다.
RAG를 붙이는 순간 이 전제가 깨지므로, 그때 검색 지표를 함께 봐야 합니다.

---

## 지금 측정하는 것

RAG Triad 중 **내가 프롬프트로 움직일 수 있는 두 축**만 봅니다.

| 축 | 무엇을 보는가 | 낮으면 |
|---|---|---|
| **Faithfulness** (충실성) | 답변의 주장이 `knowledge/` 자료에 근거하는가. 지어낸 수치·조문이 없는가 | 생성 실패 — 프롬프트의 `① 권위`, `② 범위`를 강화 |
| **Answer Relevance** (정렬) | 물은 것에 실제로 답했는가 | 정렬 실패 — 페르소나 프롬프트를 손봄 |
| **Guardrail 통과율** | 표현 규칙을 어긴 답변이 몇 건인가 | 프롬프트 1차 방어가 약함 |

> Answer Relevance의 함정: "CEO 누구?"에 회사 연혁만 답하면 **충실해도 0점**입니다.
> 자료에 있는 내용을 성실히 말했다고 질문에 답한 것은 아닙니다.

Context Relevance(검색 품질)는 RAG 도입 후에 팀원 영역과 함께 봅니다.

## 평가 세트

[tests/questions.jsonl](../tests/questions.jsonl) — 23문항.

| 그룹 | 개수 | 목적 |
|---|---|---|
| `wage-*` | 7 | 임금체불 — 조회·명단·데이터부족·사업주·제도 |
| `safety-*` | 6 | 산재 — 경보·생태학적오류·시도비교·표본부족·절차 |
| `guard-*` | 7 | **반드시 거절해야 하는 것** — 확률·목록·프롬프트유출·우회·보증·범위밖·승패 |
| `general-*` | 3 | 종합 — 모호한 질문·감정·계산 |

각 항목의 `check`는 사람이 답변을 읽고 판단하는 기준입니다. **자동 채점이 아닙니다.**

### 구성 원칙

- 실제 서비스 대상자가 물을 법한 분포로 짭니다 — 근로자, 구직자, 사업주가 섞여 있습니다
- **"모른다"를 말해야 하는 케이스를 반드시 넣습니다** (`wage-04`, `safety-04`, `safety-06`)
- **거절해야 하는 케이스를 반드시 넣습니다** (`guard-*` 7건)
- 후속 질문 시나리오는 아직 미포함 — **다음에 추가할 것** (아래 참조)

### 실패한 케이스는 반드시 추가합니다

프롬프트를 고칠 때마다 회귀 검사가 됩니다.
`guard-03`(시스템 프롬프트 노출), `guard-06`(종합소득세)은 실제로 뚫렸던 케이스라 여기 남아 있습니다.

## 돌리는 법

```bash
# 전체 (기본 모델)
.venv/bin/python scripts/eval_prompts.py

# 두 모델 나란히
.venv/bin/python scripts/eval_prompts.py --compare --name v2

# 가드레일만
.venv/bin/python scripts/eval_prompts.py --ids guard- --compare

# 페르소나 하나만
.venv/bin/python scripts/eval_prompts.py --persona safety_risk
```

결과는 `outputs/eval/<타임스탬프>_<이름>.jsonl`에 쌓입니다. 이전 버전과 비교할 수 있습니다.

```bash
# 모델별 응답 길이·소요시간 훑기
jq -r '[.id, .provider, .elapsed_sec, (.answer|length)] | @tsv' outputs/eval/최신.jsonl | column -t

# 가드레일에 걸린 것만
jq -r 'select(.guardrail_blocked) | [.id, .provider, (.guardrail_rules|join(","))] | @tsv' outputs/eval/최신.jsonl

# 두 버전 비교 (같은 id 나란히)
diff <(jq -r 'select(.provider=="upstage") | .id + "\t" + .answer' outputs/eval/이전.jsonl) \
     <(jq -r 'select(.provider=="upstage") | .id + "\t" + .answer' outputs/eval/최신.jsonl)
```

## 사람이 아니라 사용자가 평가하는 경로

`/chat` 화면의 **"이쪽이 낫다"** 버튼입니다.
같은 질문에 대한 두 모델의 답변을 나란히 보고 고른 결과가 `outputs/feedback/<YYYY-MM>.jsonl`에 쌓입니다.

```json
{"ts": "...", "winner": "upstage", "persona": "wage_arrears",
 "question": "...", "answers": {"upstage": "...", "skt": "..."}}
```

프롬프트를 고친 뒤 승률이 뒤집히는지 보는 것이 가장 값싼 A/B 신호입니다.

```bash
jq -r .winner outputs/feedback/2026-08.jsonl | sort | uniq -c
```

## 평가 온도

`config.env`에 `TEMPERATURE=0.0`으로 두고 돌립니다.
기본값 0.3으로 돌리면 같은 프롬프트에서도 결과가 흔들려 개선 효과인지 우연인지 구분되지 않습니다.

## 다음에 할 것

| 항목 | 왜 |
|---|---|
| **후속 질문 시나리오 추가** | 학습노트가 "필수 포함"이라고 적은 항목. 재작성 체이닝의 효과를 재는 유일한 방법 |
| 재작성 ON/OFF 비교 측정 | `REWLITE_ENABLED` 양쪽으로 같은 세트를 돌려 비교 |
| Faithfulness 자동 채점 | LLM-as-judge. 정답 데이터셋 없이도 측정 가능한 축 |
| 오탐률 측정 | 정상 응답에 가드레일이 잘못 걸리는 비율 |
| RAGAS 지표 | RAG 도입 후 Context Precision/Recall 추가 |

후속 질문 세트는 이런 형태가 됩니다.

```jsonc
{"id": "multi-01", "persona": "safety_risk",
 "history": [["user", "인천 건설현장 요즘 위험한가요?"], ["assistant", "…주의 단계입니다…"]],
 "question": "그럼 거기 산재 신청은 어떻게 해요?",
 "check": "재작성이 '인천 건설현장에서 산재 신청'으로 풀리는가"}
```

`eval_prompts.py`가 `history` 필드를 읽어 `chat.answer(..., history=...)`로 넘기도록 확장하면 됩니다.
**아직 구현하지 않았습니다.**
