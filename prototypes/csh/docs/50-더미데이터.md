# 가상 기업 데이터

작성 2026-08-01 · 구현 [app/demo.py](../app/demo.py)

실제 모델과 데이터가 붙기 전까지 화면과 챗봇이 완성된 형태로 돌아가게 하는 것이 목적입니다.
**공공데이터에서 실제로 얻을 수 있는 필드만** 씁니다. 나중에 실데이터로 갈아끼울 때 스키마가 그대로 맞아야 하기 때문입니다.

## 1. 필드와 출처

| 필드 | 출처 | 주기 |
|---|---|---|
| 사업장명 · 소재지(시도/시군구) · 업종 · 설립연도 | 국민연금 가입 사업장내역 | 월 |
| 가입자 수 · 신규취득 · 상실 · 고지금액 | 국민연금 가입 사업장내역 | 월 |
| 결측 개월 · 데이터 충실도 | 위 데이터의 월별 스냅샷 존재 여부 | 월 |
| 매칭 신뢰도 | 이름+주소 5단계 매칭 결과 | — |
| 체불사업주 명단 등재 · 체불액 · 공개일 | 고용노동부 체불사업주 명단공개 | 반기 |
| 건강보험 체납 등재 · 체납액 · 공개일 | 건강보험공단 고액·상습 체납 공개명단 | 부정기 |
| 업종 폐업률 | KOSIS 산업별 기업수(활동·신생·소멸) | 연 |
| 지역·업종 산재 경보 | 국민권익위 민원분석정보 + 산업재해현황 | 주 |

파생 지표(순고용변화율, 이직률, 1인당 고지금액, 하락 streak)는 위 원자료에서 계산됩니다.

**매칭 신뢰도가 왜 필요한가** — 국민연금 데이터의 사업자등록번호가 6자리로 마스킹되어 있어
번호로 조인할 수 없습니다. 이름+주소 5단계 매칭을 쓰기 때문에 동명 사업장 오매칭 가능성이 늘 남습니다.

## 3. 이름 규칙 — 법적 안전

- 접두어는 `샘플 / 데모 / 예시 / 테스트 / 가상 / 모의` 만 씁니다
- **실존 기업을 연상시키는 이름을 쓰지 않습니다.** Figma 시안에는 실명 대기업이 들어 있었지만 전부 교체했습니다
- 모든 레코드에 `is_dummy: true`
- 랜딩 상단에 "화면의 사업장·지표·게시글은 전부 가상 데이터입니다" 배너 고정

## 4. 조회는 코드로 필터링합니다 — 모델에 맡기지 않음

`app/demo.py`의 `filter_records(question)` / `filter_alerts(question)`.

질문에서 지역·업종을 뽑아 **조건에 맞는 레코드만** 프롬프트에 넣습니다.
질문에 이름이 직접 나온 사업장은 조건과 무관하게 포함합니다.

```
"인천 건설업에서 일할 만한 곳"  → [지역: 인천 · 업종: 건설]
                                  샘플A건설, 데모F전기공사, 샘플J건설
"제주도 숙박업 추천"            → [지역: 제주 · 업종: 숙박]  없음
"샘플A건설 어때요?"             → 이름 매칭으로 포함
```

학습자료가 적은 대로입니다.

> 재식별 방지 3종 세트는 **프롬프트가 아니라 DB 쿼리 계층에 코드로** 구현합니다.

실제로 프롬프트로만 시도했을 때 두 모델 다 조건을 무시했습니다 — 5절 참조.

## 5. 이 데이터로 잡은 문제 4가지

가상 기업 데이터를 늘리자마자 **프롬프트만으로는 못 막는 문제**가 연달아 드러났습니다.
전부 실제 서비스였다면 법적 문제가 되는 유형입니다.

### ① 조회되지 않는 회사의 수치를 지어냄

> 👤 삼성전자 기흥사업장 어때요?
> 🤖 최근 12개월간 가입자 수가 **1,200명에서 1,150명으로** 감소…

조치 — `<workplace_db>` 블록으로 조회 결과를 주입하고 "여기 없으면 찾지 못했다고 답하라"를 명시.

### ② 미등재 사업장을 "체불 명단 등재"라고 단정 ⚠️ 가장 위험

> 🤖 체불사업주 명단에 등재된 곳은 예시C물류와 **샘플J건설** 두 곳입니다.

샘플J건설은 **미등재**입니다. 정부 명단 등재는 사업장 신용에 직접 영향을 주는 사실이라
틀리면 그 자체로 명예훼손이 됩니다. 정규식으로는 잡을 수 없습니다.

조치 — `inspect_facts()` 데이터 대조 검증 신설. 답변에 등장한 사업장명을
실제 레코드와 맞춰 보고 어긋나면 차단합니다 (`false_listing`).

### ③ 여러 사업장을 나열하며 위험 서술

> 🤖 나머지 사업장(샘플A건설, 데모F전기공사 등)은 명단에는 없지만 위험 신호가 관찰되고 있습니다.

순위 형태가 아니어도 **사실상 "위험 사업장 목록"** 입니다.
조치 — `multi_named_risk` 규칙 + 프롬프트 7절에 "순위 형태가 아니어도 마찬가지" 명시.

### ④ 존재하지 않는 회사를 통째로 창작

> 👤 제주도 숙박업에서 안정적인 곳 추천해줘 (조회 결과: 0건)
> 🤖 - **제주그린호텔** – 최근 12개월간 가입자 수 감소가 관찰되지 않았습니다.
>    - **제주오션리조트** – 12개월 모두 데이터가 존재하고…

이름 자체가 가짜라 ②의 대조 검증으로도 안 잡힙니다.
조치 — `fabricated_workplace` 규칙. 답변에서 굵게 표시된 사업장 이름 중
**조회 결과에도 없고 사용자 질문에도 없는 것**이 데이터 서술과 함께 나오면 차단합니다.

같은 문제가 **산재 경보**에서도 났습니다("제주 숙박업 주의 단계" — 그런 경보는 없음).
`<safety_alerts>` 블록도 같은 방식으로 조회 결과만 주입하도록 바꿨습니다.

## 6. 남은 한계

| 항목 | 메모 |
|---|---|
| 지역·업종 추출이 키워드 매칭 | "수도권", "중부지방" 같은 표현은 못 잡습니다. 실DB에서는 코드 테이블로 |
| 굵게 표시하지 않은 창작 이름 | `fabricated_workplace`는 `**볼드**`를 신호로 씁니다. 평문으로 지어내면 놓칠 수 있습니다 |
| 이직률·고지금액의 업종 평균 | "동종업계보다 높다"의 기준값이 아직 없습니다 |
| 산재 경보 10개 조합만 존재 | 17시도 × 19업종 중 일부입니다 |

## 7. 실데이터로 갈아끼울 때

바꿀 곳은 세 군데뿐입니다.

1. `demo.filter_records()` → 실제 DB 질의 (사업장명 5단계 매칭 포함)
2. `demo.filter_alerts()` → 경보 테이블 조회
3. `chat._fact_records()` → 같은 조회 결과를 가드레일에도 전달

프롬프트 쪽 계약(`<workplace_db>`, `<safety_alerts>` 태그)과 가드레일은 그대로 씁니다.

**가드레일에 넘기는 레코드는 프롬프트에 넣은 것과 반드시 같아야 합니다.**
다르면 정상 답변이 차단되거나(오탐) 창작이 통과합니다(미탐).
