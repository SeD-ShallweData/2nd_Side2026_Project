# Money Worry 개인 후속 작업 공통 계약

## 2026-09-23 인수 상태 및 과업 관계 정정

사용자 확인에 따라 **01·02는 각 보고서에 적힌 범위에서 완료**, **03은 03-A의 코드·검증을 마쳤으나 교차 회사 귀속/회상과 최종 빌드 실측 등 03-B가 남아 전체 미완료**다. [03 보고서](../qa/2026-09-23-personal-03.md)를 기준으로 재개한다. 01의 전체 baseline PARTIAL과 02의 로컬 A/B/C 비교 완료를 혼동하지 않는다. 아래의 기존 '6단계 순서'는 처음 작성한 과업 분류 기록이며 **04는 01 이후 별도로 진행**, **05·06은 별개 과업**이다. 03 이후 04·05·06을 자동 진행하지 않는다. 팀원의 운영 증거와 독립 평가, 사용자의 최종 전체 QA도 별도 대기다.

03-A에서는 정정/약속 부재, 다음 행동 질문, AQ21 오교체, AQ32 기한 표현, 인용만 남는 생성 답변을 수정했다. 실제 Chrome 합성 계정에서 저장·복원·재로그인과 삭제 전용 계정 제출/DB 삭제/로그인 거부를 확인했다. 새 격리 DB의 B 회사 행 누락은 실행기 오류로 수선했지만, A 문맥에 B의 사용자 진술이 섞일 수 있고 두 회사 지급 약속을 함께 묻는 질문이 실패했다. **03-B의 첫 재현/수정 대상**이며 최종 빌드의 브라우저 재검증도 필요하다. 운영 적용 증거로 확대하지 않는다.

기준일: 2026-09-23 KST. 개인01 뒤 사용자 지시에 따라 **개인02를 로컬 기억 방식 A/B/C 비교로 구체화**했다. 제품 개선은03으로 넘긴다. 03~06은 아직 시작하지 않았다.

**개인02 결과 확보 완료**: [기억 비교 보고서](../qa/2026-09-23-personal-02.md). Node22.23.2/Next16.3.5 정합화, 새 격리PG16의 기존migration/owner/summary/연속저장 검증, Upstage 유효비교24건+기존오류진단3건. 실제81호출/215,413tokens(무효 도구중단2호출 포함), 자동retry0. 원문 B도 회사간 약속 혼입, C는압축 손실과 남은 사실 무시, A/C는답변 반복을 관측했다. 동일 입력의 F05 결과도 달라 단일 실행으로 방식 우열을 확정하지 않는다. 제품 수정·운영 검증·사용자 인수는 하지 않았으며 **03 시작 지시 대기**다.

## 목적과 현재 기준

답변 품질과 대화 기억의 기존 구현을 보존하면서 관측된 실패부터 개선한다. [09-17 계획](2026-09-17-answer-quality-and-memory.md)의 baseline → 계약 → 원인별 수정 원칙을 계승한다. 당시의 “영속 저장 미구현” 상태는 현재 상태가 아니다. [후속 01~10](../qa/2026-09-21-followup-10.md)의 완료 증거와 [이번 baseline](../qa/2026-09-23-personal-01.md)을 함께 사용한다.

사용자는 `task/reply-prompt-upgrade`가 main과 동일하고 최신 서버 배포가 끝났다고 설명했다. 브랜치/main 비교와 원격 조회를 다시 하지 않았다. 이 설명을 운영 migration·권한·저장 모드·worker·정책의 검증 증거로 확대하지 않는다. 과거 보고서의 병합 대기 지시는 현재 할 일로 재등록하지 않는다.

## 증거 기준과 비용 중단 기준

각 실행은 제품 HEAD, 실제 소스 해시, evaluator 해시, 실제 Node/Next/Python/model, prompt 해시, 데이터 모드, RAG 자산, 시각과 loopback 주소를 남긴다. branch 동일성 확인은 이번에 재실행하지 않는다. 설치 의존성이 lock과 다르면 해당 결과를 동일 빌드의 검증이라고 부르지 않는다.

다음 판정은 합쳐서 하나의 PASS로 만들지 않는다.

1. HTTP/요청: status, parse/network error, duration.
2. 최종 답변 계약: PASS/FAIL/ORACLE_UNCERTAIN/NOT_EVALUATED와 실패 조건.
3. 유용성·출처 검토: 질문 직접성, 적용 조건, 다음 행동, 실제 표시 출처. 검토자와 한계.
4. 원시 생성: 분류/재작성/최종 생성 출력 구분, 내용 오류와 단순 표현 누락 분리.
5. 가드레일: passed/replaced/fallback/short_circuit, hit, 교체 전후 의미, 과잉 교체 후보.
6. 저장/복원: guest/client history, Mock repository, real PG, HTTP restore, browser restore를 구분.
7. 계측: chat 요청 수와 내부 provider 호출 수, 실제 returned usage, 지연, 실패·재시도. usage 없음은 null/미측정이며 0으로 보충하지 않는다. 금액과 TTFT도 실제 증거 없으면 미측정.

개인01 live 묶음: 개발 고정 9건(내부 예상 0~27회), guest 연속 6턴(0~18회), 전체 hard cap **40회**, 각 1회. 인증/금지/한도 응답 401·403·429, 연속 upstream 실패 2회, call cap, 로컬 준비 실패에서 중단. evaluator 자동 재시도 0회. 환경 차단이 해소되어 재개할 때 이전 실행을 덮어쓰지 않고 별도 묶음으로 기록한다. 계약 FAIL은 결과를 보존하고 원인 검토 없이 반복하지 않는다.

개인02 live 묶음: 고정36+연속36+현재service진단6~9호출 예상, 누적cap90. 최초 전체prompt 검사에서 중단된1행은INVALID로 제외하고, 기억예산4096/입력payload를 바꾸지 않은 채 검사상한만8192→12288로 수선했다. 유효10행을 보존해 나머지만 재개, 실제32+49=81호출. 요약은기존extractive-v2/LLM0회이며 원시·최종 모두 무응답/회사귀속 오류가 남았다. 이 결과의 **현재 제품 회상 shortcut 우회·고정 retrieval·반복 assistant fixture·한 번의 표본** 한계를03에서도 유지한다.

## 팀원에게 받을 운영 증거 체크리스트

아래는 **회신할 증거의 형식**이다. 운영 명령 실행 지시나 담당자 배정이 아니며, 이번에는 외부 전송도 하지 않았다. 각 항목에 `확인 시각 / 대상 환경 / SHA 또는 artifact 버전 / 비밀 제거 결과 / 미확인 사유`를 붙인다. 상태는 현재 모두 **회신 대기**다.

| 항목 | 요청할 증거 | 판정 한계 |
| --- | --- | --- |
| 실행 버전 | 실제 serving app SHA/build와 worker artifact SHA, instance 범위 | “최신 배포” 메시지로 DB/worker까지 추정 금지 |
| migration | 대상 PG major, ledger/hash/시각 및 read-only drift 결과. 현재 정의 기준 0000~0020/21 entries, known postconditions/pending 여부 | SQL 파일 존재·CI 성공은 운영 적용 증거 아님. drift면 운영자가 별도 절차로 처리 |
| 최소권한 | app auth/conversation/worker 실제 role 이름과 필요한 CRUD/거부 smoke 결과, 비밀번호 제거 | role 생성 스크립트 존재는 실제 grants 증거 아님. 기능 role을 사용자별 RLS라 부르지 않음 |
| 실제 저장 모드 | auth/conversation real의 **유효 설정**, 대상 DB 식별(비밀 제외), 합성 저장→detail→재로그인 결과 | APP_DATA_MODE 기본값만으로 판단 금지. 회사 mock/real과 대화 모드를 별도 기록 |
| worker/timer | 별도 bundle build/install 버전, unit/timer 활성·최근/다음 실행, exit code와 처리 개수 | Next 배포 성공이 worker 설치를 대신하지 않음 |
| backlog | 만료 대상 수/가장 오래된 시각, summary pending/failed/stale lease 수, 처리 전후 추세 | 상담 내용/계정 목록은 받지 않음. 한 번 0건 tick만으로 모든 복구 PASS 금지 |
| shared quota/proxy | 다중 instance 합산 제한의 위치·효과, forwarding header 정규화, 익명 429 synthetic evidence | 현재 코드 map은 process-local. same-origin은 인증·quota identity가 아님 |
| 알림/예산 | 실제 provider budget 차단/경보 설정과 테스트 또는 수신 증거(값·연락처 비밀 제거) | 개인 작업에서 새 결제·자동 충전·비용 설정 변경 금지 |
| backup TTL | 보관 catalog의 생성/만료 정책과 최대 30일 적용 증거 | live DB 30일 expiry는 backup 30일 증거 아님 |
| 복구 후 삭제 | 격리 restore 리허설에서 cutoff와 삭제 journal/tombstone 재적용, 서비스 개방 전 재노출 방지 결과 | live hard-delete만으로 backup 복구의 삭제 유지 주장 금지 |
| 외부 AI/피드백 | 실제 공급자 보존·무학습·지역·삭제 조건의 계약 근거, feedback OFF 유효 설정 | 문서상의 희망 조건≠계약. 비교 피드백 저장 구현은 이번 6단계 밖 |

## 보류

MAS, 새 memory event/consent 테이블, cross-feature 계약 분석 기억, 비교 피드백 저장/ledger/90일 purge, 특권 감사 UI, README 전면 개편, 신규 결제 설정은 이번 순서에 끼워 넣지 않는다. SKT/Responses live 비교는 Upstage의 결과와 별도의 승인된 측정 묶음으로만 다룬다. 구현된 대체 경로가 운영에서 활성이라는 가정은 하지 않는다.
