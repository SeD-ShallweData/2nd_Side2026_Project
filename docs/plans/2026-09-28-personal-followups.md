## 04 실행 전 측정 계약

현재 질문 / 생성 직전 messages / 공급자 원시 content / finish_reason·usage / 최종 답변 / guard 판정을 각각 Git 제외 runtime에 보존한다. 합성 자료만 기록한다. 이전03은 prompt hash만 남겨 정확한 원래 입력 replay가 불가능하므로 동일 제품 경로로 만든 최소 사례와 역사 증거를 구별한다.

1. 고정 질문·사용자 사실·근거·모델 설정을 유지한 진단: 반복 합성 fixture와 제품 회상 답변 이력 **2종 × 3조건 × 2회 = 12 generation 호출**. 조건은 현재 압축/native 역할, assistant 전체문/native 역할, 같은 전체문을 과거 기록 데이터로 묶은 역할이다. 현재 질문은 마지막 user 메시지로 유지한다. 요약 유무 등 다른 요인은 고정한다. 기대답은 입력하지 않는다.
2. 원인에 맞춘 수정 후 같은 두 입력 **각2회 = 4 generation**. 필요시 요약 포함 사례 **수정 전/후 각2회 = 4 generation**를 별도 진단한다. 같은 입력의 반복과 수정 전후는 hash로 구별한다.
3. 실제 서비스 경로: 수정 전/후 각각 실제 답변이 누적되는 **4턴(최대12호출씩)**. 순수 회상은 provider0이며 강제 생성하지 않는다. 서문 반복으로 채운 fixture와 제품이 실제 반환한 이력을 구별한다.
4. 예상 최대44호출, 세션 누적 hard cap **48**. 401/403/429, 연속 upstream 실패2회, 입력/계측 무결성 실패에서 중단. 자동 재시도0. 도구 오류는 무효 행과 비용을 보존하고 영향 부분만 재개한다. 추가 실험이 필요하면 실행 전에 근거와 별도 상한을 기록한다.
5. raw 무응답(질문의 사실/행동에 실질적인 답 없이 확인/서문만), 요구 사실·행동·근거 충족, guard 교체, 최종 유용성, 호출·반환 token·지연을 따로 평가한다. 짧은 정상 회상은 무응답이 아니다. 금액/TTFT 미측정을0으로 채우지 않는다.

결과와 재현 절차는 [04 보고서](../qa/2026-09-28-personal-04.md)에 기록한다. 작은 개발 표본의 성공은 일반 raw 문제 완전 해결·최종 품질 허용 판정·운영 인수를 의미하지 않는다.

### 04 제한 보완 — 최초 전후38호출 이후, 실행 전 추가

최초 수정 후 서문만 생성하는 실패는0/9였지만 연속turn10이turn9 본문과 완전히 같고 문장별 근거가 누락됐다. 전체 재실행 대신 같은 마지막 질문·원문 문맥을 고정한 보완 검사를 한다. 긴 제공 자료 뒤에도 현재 질문의 요구와 문장별 근거 계약을 명확히 남기도록 생성 직전 출력 계약을 보완한다. 제품 회상 고정 입력2회 + 실제 연속turn10 입력 replay2회 + 같은turn10 현재service경로1회(최대3호출), **추가최대7/누적최대45**, 기존hard cap48 유지. 이는 새 연속 대화5회가 아니라 고정 replay이며 표본을 합쳐 연속 성공률로 계산하지 않는다.
