# 답변 품질 전면 개선 및 대화 기억 구현 계획

작성일: 2026-09-17

## 0. 목표와 현재 상태

최우선 목표는 **사용자의 실제 질문과 대화 맥락에 맞는 정확하고 유용한 최종 답변**이다. 대화 기억은 이 목표를 달성하기 위한 기능으로 함께 구현한다. 창의가 프롬프트·분기·RAG·가드레일·기억 DB/API/UI·평가를 끝까지 맡는다. 팀 역할 분담이나 다른 주간 과업은 이 계획의 선행조건으로 두지 않는다. 작업은 사람이 아니라 검증 가능한 변경 단위로 나눈다.

이 문서는 계획이며 구현 완료 보고서가 아니다. 새 대화창에서 구현을 시작할 때 이 계획을 따른다. 기존 실험 프롬프트는 평가 세부 참고자료로 사용하고, 범위·순서·담당·기억 구현에 관해서는 이 최신 계획을 우선한다.

이번 계획 작성 시 확인한 기준:

- 로컬 HEAD는 PR #96이 반영된 `3b3d484`이며 추적 작업 트리는 깨끗했다. 원격 최신 상태와 실행 서버 버전은 새 작업 시작 시 다시 확인한다.
- #96은 회사 문맥 질문, 업무 배경이 섞인 노동 질문, 출력 가드레일을 개선했다. 답변 구조 전체가 검증된 것은 아니다.
- `product/eval/chat-quality-cases.json`에 A~L 60개 사례, holdout 24개가 있다. 계약 테스트는 주로 필드·개수·분류 구성을 검사한다. 사례를 실제 대화로 실행해 답변 내용까지 판정하는 평가가 추가로 필요하다.
- `product/eval/README.md` 기록은 소규모 실제 Upstage 평가다. v8의 두 대표 질문에서 원시 출력 5/6, 가드레일 포함 최종 응답 6/6이었다. 전체 정확도로 일반화하지 않는다.
- `docs/prompt/2026-09-17-positive-signals-live-check.md`에는 이전 시연 서버에서 회사 자료를 받았는데도 ‘답변 작성 지침’을 최종 답변으로 출력하고 가드레일을 통과한 사례가 있다. 당시 정책 버전은 v6이며 #96 이후에도 재현되는지는 미확인이다.
- 대화 영속 저장 테이블·목록/상세/삭제 API는 현재 확인한 코드에 없다. 기존 `conversation_id`와 클라이언트 recent_messages는 영속 기억 구현과 다르다.
- 최신 팀 노션 QA 페이지는 이 연결에서 404다. 새 QA 원문 전체를 읽었다고 주장하지 않는다. 원문 확보는 아래 1단계의 남은 입력이다.

현재 로컬 환경의 과거 인수인계는 회사 Mock + 실제 RAG + 실제 Upstage다. RAG 포트가 5051에서 별도 후보 5052로 변경된 기록이 있으므로 고정 포트를 가정하지 않는다. 기억 기능에는 별도의 새 로컬 PostgreSQL이 필요하다. 회사 데이터까지 Real DB로 바꿀 필요는 없다.

## 1. 먼저 ‘좋은 답변’의 기준을 고정한다

좋은 답변은 단순히 가드레일을 통과한 답변이 아니다. 다음 다섯 조건을 함께 충족해야 한다.

1. 지금 물은 것에 답한다. 회사 질문과 개인 노동 문제를 혼동하지 않는다.
2. 사용자가 이미 준 정보를 활용하고, 없는 사실은 만들지 않는다.
3. 법률·회사 관련 실질 주장에 맞는 근거가 있고 적용 범위·시점을 지킨다.
4. 필요한 확인 질문이나 다음 행동이 구체적이다. 대답할 수 있는데 계속 되묻거나 같은 회사 요약을 반복하지 않는다.
5. 위험한 단정, 내부 지침 노출, 다른 사람/회사/상담방 정보 혼입이 없다.

이 기준을 각 시나리오의 **답변 계약**으로 만든다. 답변 계약에는 반드시 답할 내용, 사용 가능한 근거, 금지할 추론, 필요한 질문, 답변을 중단할 조건, 사용자가 다음에 할 수 있는 행동을 적는다. 문장 하나의 완전 일치를 정답으로 삼지 않는다.

예시:

| 상황 | 좋은 답변의 핵심 | 실패 예 |
|---|---|---|
| 선택 회사의 ‘추가 확인’ 표시 이유 | 공개 자료의 실제 상태·의미·한계를 설명. 개별 원인이 없으면 없다고 명시 | 다시 질문 목적부터 묻기, 체불 기업이라고 단정 |
| ‘긍정 지표 0개’의 일반적 의미 | 회사 선택 없이도 설명 가능한 일반 의미와 특정 회사의 확인 필요를 구분 | 무조건 회사 선택 요구 |
| 임금 문제를 말한 뒤 ‘그럼 어디에 문의해?’ | 해당 노동 문제의 맥락을 이어받아 적합한 확인 창구 설명 | 회사 요약으로 전환, 같은 사실 다시 질문 |
| 노동 질문을 충분히 설명했지만 RAG 장애 | 자료 조회 실패를 알리고 확인 가능한 다음 경로 제시 | 사용자가 설명을 더 해야 한다고만 반복 |
| 회사 지표와 실제 야근 문제를 함께 질문 | 관련성이 있는 복합 요청이면 각각 필요한 자료로 답하거나 핵심 한 가지 확인 | 모든 복합 요청을 무조건 unclear 처리 |
| 노동 상담과 투자 추천을 함께 요구 | 답할 수 있는 부분과 범위 밖 부분을 명확하게 나누는 방안 평가 | 투자 조언 생성, 정상 노동 상담 전체 차단 |

마지막 두 행은 현재 동작을 그대로 유지하겠다는 의미가 아니다. 현 정책의 복합 요청 처리도 품질 관점에서 재검토한다. 두 방식을 같은 사례로 비교하고, 선택한 행동을 정책 문서와 테스트에 함께 반영한다. 근거 없는 법률 답변이나 비공개 값 공개를 허용하는 정책 변경은 포함하지 않는다.

## 2. 전체 진행 순서

| 단계 | 수행 내용 | 다음 단계로 넘어갈 조건 |
|---|---|---|
| 1 | 최신 QA 수집·재현과 환경/버전 고정 | 실제 불만을 재실행할 입력과 기대 행동이 있음 |
| 2 | 시나리오·답변 계약·평가 실행기 구축 | 결과를 모델 출력까지 확인하며 반복 측정할 수 있음 |
| 3 | 실패 원인 분석과 목표 답변 흐름 설계 | 실패가 시작된 단계와 바꿀 책임이 연결됨 |
| 4 | 단일 질문·짧은 대화의 답변 구조 개선 | 기억 저장 없이도 핵심 정상/범위 밖 질문을 제대로 처리 |
| 5 | 기억 저장·복원·삭제와 UI 구현 | 서버 재시작 후 복원, 소유권·중복·삭제 검증 통과 |
| 6 | 구조화 요약과 장기 문맥 연결 | 요약을 써도 사실·정정·회사·미해결 질문이 유지됨 |
| 7 | 전체 회귀·부정 테스트·성능과 비용 비교 | 실제 QA와 독립 평가셋의 전후 결과, 잔여 실패가 정리됨 |
| 8 | 실제 화면·배포 환경 인수 검증과 인계 | 확인한 범위에서 재현 사례가 닫히고 실행/복구 방법이 있음 |

기억이 필요한 시나리오와 문맥 인터페이스는 2~3단계부터 설계한다. 다만 구현·효과 측정은 짧은 문맥 → 영속 원문 → 구조화 요약 순서로 진행한다. 그래야 기억 추가로 해결된 문제와 생성/검색 개선으로 해결된 문제를 구분할 수 있다.

## 3. 단계 1 — QA를 재현 가능한 문제 목록으로 바꾼다

### 3.1 입력 수집

노션 QA 원문, 사용자 제보, 기존 평가 기록을 모은다. 원문 접근이 안 되면 접근 가능한 브라우저나 사용자가 제공하는 내보내기·붙여넣기를 이용한다. 출처 접근 문제 때문에 알려진 재현·기존 코드 분석까지 멈추지 않는다. 다만 모든 팀 QA를 검증했다고 표시하지 않는다.

각 QA는 다음 정보를 가진 한 건의 이슈로 정리한다.

```text
qa_id / 원문 위치 / 제보 시각 / 실행 시각 / 로컬 또는 서버 버전
질문 원문 / 직전 대화 / 선택 회사 / 진입 화면 / 상담 모드
실제 최종 답변 / 화면 출처와 버튼 / trace
기대하는 행동 / 왜 잘못됐는지 / 위험도 / 재현 여부
관측 사실 / 원인 가설 / 확인하지 못한 정보
```

비슷한 제보는 원인 후보로 묶되 원문 사례 ID는 유지한다. 질문만 있고 직전 대화가 없으면 ‘맥락 불완전’으로 기록한다. 화면 캡처만으로 분류기나 모델의 책임을 확정하지 않는다.

### 3.2 기준선 보존

- 코드 SHA, 프롬프트 실제 내용 해시, 모델, 데이터 모드, RAG 자산, 실행 포트와 시간대를 기록한다.
- 회사 자료·이력·검색 근거를 fixture로 고정한 실험과 실제 검색을 거친 통합 실험을 분리한다.
- 합성 입력의 답변 원문과 가드레일 교체 전/후를 안전한 로컬 평가 산출물에 남긴다. 요약 trace만 남겨 내용 평가가 불가능해지지 않게 한다.
- 실제 QA의 개인 정보는 익명화하되 문제가 되는 의미를 유지한다. 인증정보·계약서 원문·내부 ML 값은 공유 산출물에 넣지 않는다.

산출물: `qa-inventory`, 재현 입력, 기준선 실행 결과, 미확보 목록.

## 4. 단계 2 — 시나리오와 실제 답변 평가기를 만든다

기존 A~L 평가셋을 확장한다. 정확히 60개여야 한다는 검사는 실질 커버리지 검사로 바꿀 수 있다. 실제 QA와 기억 시나리오가 추가될 때 개수 제한 때문에 누락시키지 않는다. 기존 holdout 24개가 이미 수정·디버깅에 사용됐다면 새 독립 평가셋을 만들고 이름만 holdout인 상태를 피한다.

### 4.1 시나리오 축

| 축 | 필수 사례 |
|---|---|
| 정상 노동 상담 | 임금·계약·근로시간·휴가·해고 등, 충분/불충분한 사실과 근거 |
| 회사 자료 | 실제 표시 설명, 일반 용어 설명, 공식 명단, 신호 미확인, 만료·부분 자료 |
| 범위 경계 | 순수 범위 밖, 범위 밖 단어가 업무 배경인 노동 질문, 복합 의도 |
| 표현 변화 | 구어체·오타·부정·인용·영어 혼용·짧은 지시어 |
| 대화 흐름 | 후속 질문, 사실 정정, 주제 전환, 이미 답한 질문, 미해결 질문 |
| 회사 전환 | 선택 없음/A/B/해제/동명 회사/대화 중 다른 회사 명시 |
| 근거 문제 | 검색 성공이지만 무관, 부분 일치, 잘못된 조문 적용, 공식 안내만 있음, 최신성 차이 |
| 실패 경로 | 분류·재작성·RAG·회사 조회·생성·저장·요약 실패를 각각 주입 |
| 출력 품질 | 지침을 답으로 출력, 질문 재진술만 함, 장황함, 반복, 가짜 인용, 답변 대신 면책 |
| 기억 수명 | 새로고침·재로그인·서버 재시작·다른 탭·삭제·만료·탈퇴 |
| 격리와 경계 | 다른 사용자/대화방 정보, 내부 필드, 프롬프트 주입, 승인 없는 감독관 자료 전송 |
| 긴급/계약서 | 긴급 안내 우선, 과거 사고와 구별, OCR 불확실과 누락 구분, 도구 부분 성공 |

최소한 다음 대화 흐름을 별도 묶음으로 만든다.

1. 임금 미지급 설명 → 지급일 추가 → 문의처 질문 → 사용자가 금액·기간 정정 → 필요한 다음 행동.
2. 회사 A의 표시 질문 → 지표의 일반 의미 → 개인 노동 문제 → 회사 B 선택 → B에 대한 질문.
3. 노동 상담 → 완전히 다른 범위 밖 주제 → 노동 상담 복귀.
4. 실제 사용자가 말하지 않은 내용을 이전 assistant가 추측 → 다음 답변과 요약이 그 추측을 사실화하는지 검사.
5. 10개를 넘는 완료 메시지 → 요약 → 사용자의 사실 정정 → 재로그인 후 이어하기.
6. 대화 진행 중 삭제/만료 → 늦게 도착한 모델 응답·요약 작업이 대화를 되살리는지 검사.

### 4.2 평가 실행기

실행기는 `/api/chat`의 실제 통합 경로와 fixture 기반 각 단계를 모두 다룬다. 합성 분류 결과를 넣은 단위 테스트만으로 의미 정확도를 주장하지 않는다.

대화 테스트에는 두 실행 방식을 둔다.

- 고정 이력 재생: 매번 동일한 이력을 넣어 특정 단계의 전후 차이를 측정한다.
- 연속 대화: 앞 턴에서 실제로 생성된 최종 답변을 다음 턴에 넘겨 오류 누적과 기억을 검사한다.

판정은 `PASS / FAIL / BLOCKED / NOT_RUN / ORACLE_UNCERTAIN`으로 나눈다. 법률 기대값은 공식 원문·적용 요건·사건 시점을 확인해 정하고, 정답이 불확실한 사례를 오답 통계에 섞지 않는다. 평가자가 확인한 웹 자료를 앱이 실제 받은 근거처럼 취급하지 않는다.

핵심 점수:

- 사용자의 질문에 실제 답했는가.
- 사실·주장·인용·적용 조건이 맞는가.
- 정상 질문을 불필요하게 차단/재질문했는가.
- 기억이 필요한 정보를 보존하고 정정을 반영했는가.
- 사용자에게 보인 최종 답변과 가드레일 이전 생성은 각각 어땠는가.
- 지연·전체 호출 수·요약 호출까지 포함한 비용은 얼마인가.

LLM 채점은 보조로 쓸 수 있지만 단독 판정자로 삼지 않는다. 자동 조건 검사와 공식 근거 대조, 사람이 읽을 전후 사례표를 함께 만든다.

산출물: 사례별 기대 행동, 재실행 가능한 평가기, 기준선 유형별 결과, 독립 평가셋.

## 5. 단계 3 — 답변 흐름과 문맥을 재설계한다

현재의 단일 `intent` 결과가 검색·회사 자료·거절 여부까지 모두 결정하는 구조가 실제 QA를 충분히 처리하는지 평가한다. 회사 질문이라도 관련 법률 설명이 필요할 수 있고, 회사가 없어도 지표의 일반 의미는 설명할 수 있다. 반대로 회사가 선택됐어도 범위 밖 질문에는 회사 자료가 필요 없다.

다음 책임을 분리하는 것을 목표 구조로 삼는다. 클래스/서비스 수를 무조건 늘리라는 뜻은 아니다.

```text
요청·권한·선택 회사 확인
  → 필요한 기존 문맥 복원
  → 현재 요청의 의미와 대상 확인
  → 답변 계획: 답할 부분 / 필요한 회사·법령·계약 근거 / 핵심 누락 정보
  → 필요한 자료 조회 + 관련성·최신성 확인
  → 허용된 문맥 구성
  → 근거에 맞는 답변 생성
  → 주장·인용·정보 경계·관련성 검사
  → 최종 답변 결정·화면 표시·저장
  → 완료된 대화만 기억 갱신
```

현재 근거로 설명 가능한 부분, 조건부로 설명 가능한 부분, 확인이 필요한 부분을 분리한다. ‘법령 검색 실패’, ‘회사 자료 없음’, ‘질문 불명확’, ‘서비스 장애’를 같은 상태로 취급하지 않는다. 검색을 생략했다면 실패한 것으로 기록하지 않는다.

답변 계획은 짧은 내부 데이터 계약으로 정의한다. 예를 들어 요청 목적, 대상 회사, 답변할 쟁점, 필요한 근거 종류, 답변을 바꾸는 누락 사실, 제한 이유 정도다. 이 계획이나 작성 지침이 최종 사용자 답변으로 나가면 실패다. 별도 모델 호출을 무조건 추가하지 말고 코드 규칙·기존 호출로 가능한 부분과 의미 판단이 필요한 부분을 구분한다.

문맥은 네 종류를 구별한다.

1. 사용자가 말했다는 사실: 사건의 진실이 확인됐다는 의미와 다르다.
2. 도구/공개 자료에서 확인한 사실: 출처와 확인 시점, 대상 회사가 붙는다.
3. 과거 assistant가 제공한 안내: 사용자 사실이나 새로운 법률 근거가 아니다.
4. 아직 확인되지 않은 조건·가설: 사용자 확인 전 확정값으로 올리지 않는다.

산출물: 현재/목표 흐름, 단계별 입력·출력 계약, 실패 원인과 수정 지점 매핑, 기억 컨텍스트 인터페이스.

## 6. 단계 4 — 단일 답변과 짧은 대화를 먼저 개선한다

개선 순서는 실패 빈도·피해·전파 범위로 결정한다. 심각한 내부 노출·다른 회사 혼입·위험한 법률 단정은 우선 처리한다. 그 다음 반복되는 정상 질문 차단, 잘못된 근거, 지침 출력, 무용한 fallback을 고친다.

### 6.1 분류·재작성·분기

- 회사별 조회가 필요한 질문과 일반 개념 설명을 구분한다.
- 복합 요청은 독립된 요청인지 단순 업무 배경인지 확인한다. 정상 부분 답변+제한 안내와 확인 질문 방식을 비교한다.
- 재작성 시 원문의 의도·부정·정정·회사를 보존한다. 원문과 충돌하면 잘못된 재작성문으로 검색하지 않게 한다.
- 필요한 사실이 이미 이력에 있으면 다시 묻지 않는다. 필요한 회사 자료가 없다면 지어내지 않는다.
- 중립적인 카드 질문과 화면이 실제로 넘기는 문맥을 맞춘다.

### 6.2 RAG와 근거

- 검색 결과의 주제 일치와 법적 쟁점 일치를 구분한다.
- 조문 번호가 일치해도 주장 내용·예외·적용 요건이 틀리면 잡아낸다.
- 자료 부족을 프롬프트로 채우지 않는다. 반복 실패가 지식 자산 누락에서 오면 공식 자료 보완을 별도 변경으로 수행한다.
- 검색 임계값, 질의 확장, 재순위화 등은 각각 효과를 측정해 채택한다. 원본 Chroma 보호와 기존 자산 검증 규칙을 유지한다.
- 회사 정보의 기준일·유효기간·공개 범위가 답변 문맥에서 사라지지 않는지 확인한다.

### 6.3 생성 프롬프트

공통의 근거·정보 경계 규칙과 목적별 답변 요구를 정리한다. 기존 지침을 계속 덧붙이기보다 충돌·중복·적용 범위를 정돈한다.

- 법률 설명에는 검증된 근거와 필요한 적용 조건.
- 회사 표시 설명에는 관측된 공개 사실, 뜻, 한계, 확인할 사항.
- 일반 개념에는 불필요한 회사 선택 요구 없이 설명 가능한 범위.
- 근거 부족에는 무엇을 확인하지 못했는지와 구체적 다음 경로.
- 후속 질문에는 새로 물은 부분과 필요한 맥락만.
- 범위 밖에는 적절한 안내와 범위 제한.

모든 답변을 같은 3문단·면책·기관 안내 형식으로 강제하지 않는다. 유용한 정보를 제공할 수 있는데 형식 때문에 지워지는지 검사한다. 문체 개선은 정확성 개선과 별도로 평가한다.

### 6.4 출력 검사와 복구

- 위험한 단정·내부 지침·민감정보·가짜 인용뿐 아니라 지침을 설명하는 답변, 질문을 전혀 다루지 않는 답변도 관측한다.
- 정규식이 부정·인용·동의어를 놓치거나 정상 문장을 막는 사례를 추가한다. 문자열 검사만으로 의미 정확성을 보장한다고 하지 않는다.
- 실패 종류에 맞는 fallback을 사용한다. 회사 기준 답변도 질문과 무관한 내용을 붙이면 안 된다.
- 한 번의 제한된 재생성/수정 호출이 도움이 되는지 평가할 수 있다. 안전한 근거만 사용하고 추가 호출·지연·실패 시 종료 조건을 정한다. 무한 재생성은 금지한다.
- 원시 생성 통과율, 교체율, 교체 후 유용성을 별도로 기록한다.

기존 모델에서 구조 개선 효과를 먼저 측정한다. 그 뒤에도 특정 유형이 반복 실패하면 같은 입력·근거·설정으로 다른 사용 가능한 모델을 비교한다. 모델 변경과 프롬프트 변경을 동시에 적용해 원인을 섞지 않는다.

완료 조건: 핵심 단일 질문과 짧은 후속 대화에서 개선이 확인되고, 정상 질문 회귀가 없다. 저장 기능이 없어도 틀리는 답변을 기억 추가로 덮지 않는다.

## 7. 단계 5 — 기억의 저장·복원·삭제를 구현한다

지난주 파일 두 개를 설계 기준으로 읽는다.

- `C:\Users\jcu03\Desktop\돈워리_대화기억_논리스키마.md`
- `C:\Users\jcu03\Desktop\돈워리_기억구조_설계대화_결정기록.md`

당시 사용자가 선택한 내용을 출발점으로 유지한다. 새로운 질문을 처음부터 반복하지 않는다. 사용자와 정한 설계 초안이라는 상태와 제품에 실제 구현됐다는 상태는 구분한다. 기존 문서의 팀 역할 분담은 이 계획에서 적용하지 않는다.

### 7.1 데이터와 API/UI

최초 핵심 데이터는 상담방, 질문·응답 턴, 메시지, 표시 출처, 회사 변경 이벤트다. 요약·계약 결과·단기 검색 기록·관리자 감사 기록은 해당 단계에서 연결한다. 논리 엔터티를 반드시 전부 별도 테이블로 만들 필요는 없으며 관계·삭제·조회 요구로 물리 구조를 결정한다.

| 요구 | 구현 내용 |
|---|---|
| 상담방 | 소유자, 제목, 현재 회사, 마지막 활동, 만료, 버전 |
| 턴/메시지 | 순서, 역할, 요청 중복 방지 키, 성공/실패 상태, 당시 회사, 최종 표시 답변 |
| 출처 | 그 답변에 실제 표시된 문서·링크·기준일의 안전한 snapshot |
| API | 생성·목록·상세·제목 수정·현재 회사 변경·이어하기·전체 삭제 |
| UI | 상담 목록, 새 상담, 복원, 삭제, 저장 실패 안내, 회사 전환 표시 |
| 익명 | 현재 세션 유지, 로그인 시 명시적 동의로 현재 대화 하나만 가져오기 |
| 권한 | 서버 세션 기준 소유권 검사. 임의 conversation_id/user_id로 타인 이력 접근 불가 |

로그인 사용자의 서버 저장 이력을 기준으로 문맥을 복원한다. 클라이언트가 보낸 이전 assistant 메시지를 검증된 서버 이력처럼 신뢰하지 않는다. 익명 가져오기 이력도 신뢰 수준을 명시하고 시스템 사실로 승격하지 않는다.

### 7.2 저장과 생성의 상태 관리

외부 LLM 호출 내내 DB transaction을 열어 두지 않는다. 요청을 접수·기록하는 짧은 transaction, 모델 호출, 최종 결과를 확정하는 짧은 transaction으로 나누고 재시도 가능한 상태를 정의한다.

- 더블클릭·네트워크 재전송으로 같은 질문·답변을 중복 저장하지 않는다.
- 답변 생성 실패, 답변 생성 성공 후 저장 실패, 사용자 취소를 서로 구분한다.
- 생성은 성공했는데 저장만 실패했다면 같은 답변을 저장 재시도할 수 있어야 하며 모델 재호출이 기본 복구가 되어선 안 된다.
- 다른 탭의 회사 변경·추가 질문과 충돌하면 어떤 버전으로 답했는지 고정한다.
- 삭제·만료·탈퇴 이후 늦게 끝난 생성/요약 작업이 메시지나 대화를 다시 만들지 못하게 한다.
- 사용자가 화면에서 본 최종 답변과 저장된 최종 답변을 일치시킨다.

### 7.3 보존과 데이터 경계

- 기존 초안의 대화 마지막 활동 후 30일, RetrievalTrace 7일을 출발점으로 구현한다. 자동 삭제를 실제 worker/스케줄러와 연결하고 실패 재시도·재시작을 검사한다.
- 사용자 삭제·탈퇴·만료는 메시지·요약·출처·첨부 메타·계약 결과·trace·백그라운드 작업까지 연계한다.
- 화면에 보이는 대화와 단기 기술 기록을 분리한다. raw prompt, 원시 모델 payload, ML 점수·SHAP, 계약서 원문을 기억에 저장하지 않는다.
- 공개 답변 원문에도 사용자가 입력한 개인정보가 있을 수 있다. 저장 대상 허용과 요약/외부 전송 허용을 동일하게 취급하지 않는다.
- 회사는 상담방 전체에 고정하지 않는다. 현재 선택과 메시지/턴 당시 회사를 각각 유지한다.

### 7.4 로컬 DB 검증

새 개발용 PostgreSQL에서 schema/migration과 기능별 최소권한을 검사한다. 기존 복원 DB나 GCP DB에 시험 migration을 적용하지 않는다. 회사 데이터는 Mock으로 유지한 채 대화 저장만 실제 DB로 검증할 수 있는 모드/어댑터 경계를 만든다.

순수 in-memory 저장소는 단위 테스트용으로만 쓴다. 새로고침뿐 아니라 서버 프로세스 재시작 후에도 살아 있는지 검사해야 영속 저장 완료로 인정한다.

완료 조건: 생성→대화→새로고침→재로그인→이어하기→삭제가 동작하고, 사용자/상담방 격리·중복 방지·만료·저장 실패가 검증됨. 이 단계에서는 요약 없이 원문 기반으로 품질을 비교한다.

## 8. 단계 6 — 요약을 검증한 뒤 장기 기억으로 연결한다

저장한 대화를 전부 프롬프트에 붙이는 방식으로 끝내지 않는다. 기존 초안의 ‘현재 누적 요약 하나 + 요약 이후 최근 원문 최대 10개 + 현재 질문 + 현재 필요한 회사/법령 자료’를 기준으로 문맥을 구성한다. 10개는 10턴이 아니라 완료된 사용자/assistant 메시지 기준이라는 점을 명확히 한다.

### 8.1 요약의 항목과 출처

사용자 목표, 사용자 진술, 이미 안내한 행동, 미해결 질문, 회사 연결, 계약 검토 결과를 구분한다. 각 중요한 사실에는 원문 메시지 ID, 대상 회사/사건, 유효 시점, 정정 여부를 연결할 수 있어야 한다.

- assistant의 추측을 사용자 진술로 바꾸지 않는다.
- 나중의 명시적 정정이 이전 진술을 대체한다. 정정 대상이 불분명하면 확인한다.
- 사용자 인용문 속 타인의 말을 사용자의 확정 사실로 취급하지 않는다.
- 과거 법률 설명과 회사 조회 결과는 현재도 맞는 사실로 고정하지 않는다.
- 대화에서 사용한 법령 조문을 기억했다는 이유로 현재 답변 근거로 승인하지 않는다.
- 예전 답변은 당시 출처와 함께 그대로 보여주되 새 답변의 회사 자료·법률 근거는 현재 쟁점에 맞춰 다시 확인한다.
- RetrievalTrace의 재작성 문장을 사용자의 실제 발화처럼 기억하지 않는다.

### 8.2 중복·누락·실패 처리

`summarized_through_sequence`와 요약 버전을 기준으로 어느 메시지가 요약됐는지 고정한다. 요약에 든 메시지를 다시 누적하거나 요약 전 공백을 건너뛰지 않는다. 문자 수 외에 실제 모델의 문맥 토큰 예산과 답변 공간을 고려한다.

요약은 완료된 턴 이후 갱신하고 실패 시 기존 유효 요약·원문을 유지한다. 요약 실패가 답변을 멈추게 하지는 않되, 원문이 예산을 넘으면 관련 메시지 선택/필요한 사실 확인으로 제한하고 빠진 사실을 추정하지 않는다. 재시도 횟수·지연·구버전 작업 폐기 기준을 정한다.

### 8.3 반드시 비교할 실험

동일 시나리오에서 다음 조건을 비교한다.

1. 현행 recent_messages만 사용.
2. 서버 저장 원문에서 필요한 최근 문맥을 사용.
3. 구조화 요약 + 원문 + 최신 자료를 사용.

요약 전후 9/10/11 및 19/20/21개 완료 메시지 경계, 20~30턴 이상의 긴 대화, 사실 정정, 회사 변경, 뒤늦은 응답, 삭제 중 요약, 요약 API 실패를 검사한다. 요약이 비용은 줄이지만 정확도를 떨어뜨리면 활성화하지 않는다.

완료 조건: 중요한 사용자 진술·정정·대상이 유지되고, 없는 사실이 추가되지 않으며, 반복 질문·주제 혼동이 줄었다는 전후 증거가 있음.

## 9. 단계 7 — 통합 품질 게이트

한 가지 전체 점수 대신 아래 결과를 함께 보고한다.

| 측정 | 판정 방법 |
|---|---|
| 실제 QA 해결 | 각 QA 입력과 변형을 재실행, 이전 실패와 새 결과를 연결 |
| 직접성·유용성 | 질문에 답하는 내용과 적절한 다음 행동이 있는지 |
| 사실 정확성 | 중요한 법률/회사 주장과 근거의 대응, 적용 조건·시점 |
| 오차단 | 답변 가능한 정상 질문을 거절/일반 재질문으로 바꾼 비율 |
| 무관한 응답 | 범위 밖 실행, 회사 요약 오삽입, 지침 출력 |
| 기억 충실도 | 사용자 진술/정정/회사/미해결 쟁점 보존과 새로운 사실 생성 여부 |
| 복구 품질 | 생성 실패·가드레일 교체 후에도 질문 관련성이 유지되는지 |
| 비용·지연 | 분류·재작성·생성·요약·수정 재호출을 합산한 요청당 수치 |

최종 수용 기준:

- 관측한 중대한 정보 노출, 다른 사람/회사 혼입, 긴급 안내 실패, 심각한 근거 조작이 남아 있으면 완료 판정하지 않는다.
- 핵심 실제 QA와 새 기억 기능의 필수 시나리오는 해결되거나, 재현 불가/정보 부족/제품 범위 밖이라는 근거 있는 상태가 있어야 한다.
- 핵심 수정 사례는 같은 설정에서 3회 반복 결과를 남긴다. 한 번의 성공으로 해결됐다고 하지 않는다.
- 개발에 사용하지 않은 평가셋에서도 개선이 유지되고, 기존 정상 질문의 회귀를 감추지 않는다.
- 정상 질문 전체를 거절·재질문해 오류를 줄이는 결과는 개선으로 인정하지 않는다.
- 목표 지연·호출 예산은 기준선을 측정한 뒤 정한다. 모델 가격을 확인하지 않고 비용을 추정값으로 확정하지 않는다.
- 테스트의 구조 검사 통과, 모델 실제 실행, 브라우저, DB 영속 저장, 운영 배포를 따로 표시한다.

기본 비용 운영안은 최초 실제 모델 10개 사례, 동시성 2 이하, 첫 실험 묶음 실제 외부 호출 200회 이내다. 분류·재작성·요약·재시도도 호출 수에 포함한다. 이후 전체 평가가 더 필요하면 이미 실행한 결과와 남은 호출 규모를 근거로 다음 묶음을 진행한다. 상한 도달은 전체 검증 완료가 아니다.

필수 자동 검사는 변경 범위별 단위·통합 테스트와 제품 `npm.cmd run check`, DB migration/삭제/권한 테스트, RAG 변경 시 Python/검색 평가다. Windows 권한 오류와 제품 동작 오류를 구분하고 Linux 운영 동등 검증을 별도로 남긴다.

## 10. 단계 8 — 실제 화면과 운영 인수

실제 사용자 경로를 클릭해 질문 입력, 카드 진입, 회사 선택/변경, 출처·버튼 표시, 로그인·상담 목록·이어하기·삭제를 확인한다. API가 올바른 답을 보내도 오래된 화면 상태가 다른 회사를 표시하면 실패다.

계약서 성공+법령 검색 실패, 비활성/선택 모드 `openai_responses`, 감독관 상담 등 공유 프롬프트/가드레일의 영향 경로를 회귀 검증한다. 현재 계약서 Mock은 실제 PDF 분석 검증을 대신하지 않는다. 기억의 계약 결과 저장·관리자 조회/감사·긴 대화 내부 목차는 기존 설계 범위에 남기되, 기본 답변과 소유자 저장/복원을 먼저 안정화한 뒤 완료한다. 관리자 권한이 있다는 이유만으로 일반 상담 원문 조회를 자동 허용하지 않고 전용 서버 검사·사유·감사 로그를 연결한다.

배포를 실행할 권한과 환경이 준비되면 다음을 확인한다. 준비되지 않았다면 배포 준비 완료와 운영 인수 미완료를 구분해 전달한다.

- 실제 배포 SHA·프롬프트 버전·RAG 버전과 설정.
- 대화 DB migration 및 삭제 스케줄러·요약 worker의 동작.
- 배포 전후 동일한 핵심 합성 QA.
- 기능 비활성화/이전 응답 흐름 전환 시 이미 저장한 대화를 보존하는 복구 방법.

schema 변경을 자동으로 되돌리며 사용자 데이터를 지우는 롤백을 쓰지 않는다. 새 동작 활성화와 데이터 구조 변경을 안전하게 분리한다. 공개 로그에 raw 질문/답변을 무제한 저장하지 않고 최소 진단 지표를 사용한다.

## 11. 변경을 나누는 기준과 산출물

창의가 전부 구현하되 다음처럼 되돌릴 수 있는 단위로 남긴다. 반드시 6개 PR을 만들라는 뜻이 아니라 의존성과 검증을 나누는 기준이다.

1. QA 재현·평가 실행기·기준선.
2. 요청 이해·근거 계획·분기 구조.
3. 목적별 생성 지침·출력 검사·fallback.
4. 기억 schema·API·소유권·저장 상태·목록 UI.
5. 요약·문맥 연결·삭제/만료 worker·장기 대화 검사.
6. 공유 경로·실제 화면·배포 인수 및 잔여 정리.

각 변경에는 해결하려는 QA ID, 코드/설계 차이, 전후 결과, 회귀와 남은 한계를 기록한다. 최신 main에서 시작하고 다른 변경이 들어오면 통합 영향만 확인한다. PR 제출·병합·배포는 실제 사용자 지시와 저장소 규칙에 따른다. 계획 작성 자체를 외부 작업 실행 승인으로 해석하지 않는다.

최종 전달물:

- 현재/목표 답변 흐름과 데이터 경계.
- 실제 QA에 연결된 시나리오·답변 계약·독립 평가셋.
- 재실행 가능한 평가 명령과 익명화된 전후 응답·단계별 trace.
- 구현 코드, 스키마·migration, API 계약, 기억·보존·권한·실패 처리 문서.
- 실제 모델/브라우저/실제 로컬 DB/운영 환경별 검증 결과.
- 아직 남은 실패와 재현 방법, 배포·복구 방법.
