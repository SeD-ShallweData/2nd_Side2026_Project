# Money Worry 개인 후속 09 — 백업·복원·삭제 재적용

작성/로컬 확인: 2026-09-29. 대상: 현재 작업 폴더의 소스 및 새로 만든 합성
PostgreSQL 16. 운영 VM·운영 DB·운영 백업·복원 자산에는 접근하거나 변경하지 않았다.
Git 작업, schema/migration 정의 변경, 운영 설정 변경, 외부 메시지, 실제 개인정보
출력은 없었다.

## 판정

| 항목 | 확인된 사실 | 미확인 또는 제한 |
| --- | --- | --- |
| 상담 30일 | `RealConversationRepository`가 활동 시 `expires_at`을 연장하고, 조회 시 만료를 제외한다. 유지보수 worker는 한 pass 최대 100개 hard delete한다. | 실제 운영 DB의 저장 모드·worker 성공·만료 backlog는 작업 07의 운영 담당자 확인 대기. 물리 삭제가 정확히 30일 시각에 완료된다는 증거 없음. |

업무상 백업이 존재한다고 가정하거나, 파일 하나를 발견했다는 이유로 복원 가능,
30일 TTL 준수, 삭제 재적용 완료라고 판정하지 않는다. `next-<sha>` rollback
빌드 정리는 DB 백업 정리가 아니다.

## 근거와 결함

- [개인정보 계약](../data-contract/public-ai-privacy.md)은 live 즉시 삭제,
  백업 최대 30일, 복원 전 현재 만료 cutoff와 삭제 journal/tombstone 재적용을 요구한다.
- [대화 저장소](../../product/src/adapters/real/RealConversationRepository.ts),
  [인증 저장소](../../product/src/adapters/real/RealAuthRepository.ts),
  [유지보수 문서](../../db/docs/CONVERSATION_MAINTENANCE.md)의 hard delete,
  cascade, 만료 batch를 확인했다. 인증의 `resolveSession`은
  `revoked_at IS NULL`만 허용한다. DB backup 시점 뒤의 **수동 대화 삭제와 탈퇴**는
  단순 `expires_at` 비교로 식별할 수 없다.
- 독립 삭제 원장은 현재 코드와 운영 문서에서 확인되지 않았다. 따라서 현 상태의
  오래된 백업을 서비스에 바로 연결하면 삭제 정보가 다시 보일 수 있다.
- 사용자에게 최소 원장 정책(사용자 ID·대화 ID·삭제 시각만 암호화하여 최대
  30일 보관)을 질문했고 2026-09-29 승인을 받았다. 별도 outbox schema 및
  export/운영 적용은 승인된 **정책**과 별개이며 이 작업에서 도입하지 않았다.
  새 원장 이전에 생성된 백업은 독립 삭제 증거가 없으면 연결 복원 금지다.

## 로컬 변경 및 합성 검증

- [복원 삭제 게이트](../../db/scripts/restore-deletion-replay.mjs):
  archive 파일 SHA-256과 기대 해시, manifest의 백업 시각·최대 30일·연속
  삭제 순번, `mw_restore_*` 대상명·PG16·다른 DB 연결 0을 검사한다.
  수동 대화 삭제·탈퇴·만료·세션 revoke를 한 트랜잭션에서 수행하고 0건
  사후조건과 생존 대화의 30일 만료 상한을 확인한다. 실패 시 rollback,
  재실행은 멱등이다.
- [합성 리허설](../../db/scripts/run-personal09-rehearsal.mjs):
  난수 이름과 `personal09` 라벨의 신규 tmpfs PG16에서 기존 migration
  0000~0020을 적용했다. 사용자 4명·대화 4건·세션·turn/message를 만든 뒤
  custom dump와 SHA-256을 만들고 live에서 일부 삭제·탈퇴·만료를 수행했다.
  새 `mw_restore_*` DB에 `pg_restore --exit-on-error`로 복원한 직후 대화
  4건이 다시 있었고, 게이트 뒤 생존 대화 1건만 남았다.
- 잘못된 archive 해시, 31일 TTL, 이미 만료된 백업, 삭제 순번 결손,
  다른 DB 연결과 30일 초과 만료 설정을 거절했다.
  중간 강제 실패 뒤 원래 4건 유지, 재실행 no-op, 실제 CLI의 archive 파일 해시
  재계산, 삭제 하위 message cascade, 모든 복원 session
  revoke, 삭제 대화로의 늦은 turn 쓰기 FK 거절을 확인했다.
- [런북](../../db/docs/RESTORE_DELETION_REPLAY.md)에 새 원장 설계, 격리 대상,
  freeze·복원·사전 검사·중단·복구 순서를 적었다.

검증 환경은 로컬 Node v25.9.0에서 실행한 스크립트와 pinned
`postgres:16-alpine` image다. 실제 앱 Node22/Linux/운영 DB 검증을 대신하지
않는다. 합성 manifest의 `coverage.verified`는 리허설용 입력이며, 운영에서는
독립 원장의 high watermark·감사 기록과 순번 완전성을 별도 대조해야 한다.
다른 DB 연결 차단은 검사 순간의 조건이다. 앱/worker/timer 쓰기를 물리적으로
격리하는 운영 절차를 대체하지 않는다.

## 운영 담당자 확인 대기와 적용 순서

운영 담당자가 읽기 전용으로 백업 카탈로그/저장소, custom dump와 GCE snapshot의
실제 범위, 생성·만료 설정, 최근 성공, archive 해시, DB major·migration drift,
원장 유무, 서비스 쓰기 경로를 먼저 확인한다. 현재 사용자에게 VM 명령 실행을
요청하지 않는다. 결과가 오면 대상 SHA·백업 세대·격리 위치·접근자·폐기 범위와
비용/중단 영향을 넣어 승인 가능한 실제 적용 명령을 확정한다.

현재는 outbox/독립 원장이 없으므로 실제 백업 복원을 서비스에 연결할 조건을
충족하지 못했다. 원장 도입에는 새 schema/migration 및 운영 저장소/권한 변경이
필요하다. 이 작업의 금지 범위이므로 설계까지만 수행했다. 해당 작업을 별도
허가 후 구현하고, 원장 시작 이전 백업은 살아 있는 정본과 완전 대조가 가능한
경우에만 검토한다. 운영 백업으로 새 격리 복원을 하는 일 역시 대상·개인정보
접근·폐기·중단/복구가 특정된 승인이 필요하다.

**코드·합성 리허설: 완료. 운영 백업/30일 TTL/실제 원장/운영 복원 검증: 미완료.**
작업 07·08의 운영 확인도 별도 대기이며 이번 결과로 완료 처리하지 않는다.

## 사용자가 직접 해야 할 행동 — Git 제외

현재 즉시 할 행동은 **없음**. 최소 원장 보존 정책 선택은 이미 답했고,
사용자는 운영 VM에 접근할 수 없다. 운영 담당자의 읽기 전용 결과가 전달되면
Codex가 적용 대상·변경·복구안을 구체화한다. 그때만 개인정보가 포함된 실제
백업의 격리 복원과 미승인 운영 변경에 대해 대상·접근·폐기·중단·예상 결과를
명시해 별도 승인을 요청한다. 지금 포괄 승인이나 VM 명령 결과를 요구하지 않는다.
