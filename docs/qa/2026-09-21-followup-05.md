# Money Worry 후속 05 - 답변 표현·복원 화면 점검

기준일: 2026-09-21  
범위: 로컬 `task/reply-prompt-upgrade`의 최종 답변 표현과 저장 대화 복원 UI. Git 쓰기, 운영/복원 DB 변경, 배포, 외부 메시지, MAS 도입은 하지 않았다.

## 재현과 원인

| 수동 QA 현상 | 원문/렌더링 경계 | 확인한 원인 | 처리 |
|---|---|---|---|
| 번호가 모두 `1.` | 원문은 항목마다 `1.`이고 설명·빈 줄·중첩 목록이 섞인 Markdown | `SafeMarkdown`이 연속된 표식 줄만 한 `<ol>`로 묶었다. 설명 또는 빈 줄마다 새 `<ol>`이 생겨 브라우저가 매번 1부터 표시했다. | 줄 치환이 아니라 목록 블록 파서로 변경했다. 같은 들여쓰기의 순서 목록은 빈 줄을 건너 계속 묶고, 항목 설명과 중첩 `ul`/`ol`을 해당 `li`에 보존한다. |
| 복원 시 사업장 ID 노출 | 대화 상세 DTO에는 ID만 있었고, 클라이언트는 현재 페이지와 같은 ID일 때만 현재 이름을 재사용했다. | 다른 상담방을 복원하면 welcome/현재 문맥/과거 사용자 턴이 raw ID를 표기했다. | 상세 API가 활성 사업장과 각 turn의 공개 회사명을 best-effort로 붙인다. 조회 실패는 상세 복원을 실패시키지 않고 `null`을 반환하며 UI는 raw ID 대신 `선택 사업장`/`연결된 사업장`으로 표시한다. 과거 turn의 회사 ID 자체는 바꾸지 않는다. |
| `Upstage Solar:`가 본문에 섞임 | 화면 카드 헤더의 provider label은 의도된 표시지만, 비교 이력은 `provider_label: answer`를 다음 요청 `recent_messages`로 보냈다. | 접두어가 다음 생성 프롬프트로 재유입할 수 있었고, 이미 저장된 응답도 본문에 그대로 렌더링했다. | 비교 이력에는 정제된 answer만 넣고, Dual/Responses 생성 결과·저장 직전 응답·렌더링에서 line-start provider 접두어를 제거한다. 카드 헤더의 provider/model 표시는 유지한다. |
| `[이전 답변 근거: ...]` 노출 | 기존 정제는 닫힌 대괄호 형태만 제거했다. | 줄 단위 history 주석 또는 이전에 저장된 응답은 UI까지 남을 수 있었다. | 닫힌/줄 단위 history annotation을 모두 최종 answer 경계에서 제거한다. 실제 `출처:` 텍스트와 `DataSourceList`는 제거하지 않는다. |

`publicAnswerText`는 공개 표시/프롬프트용 정제 함수다. 저장된 과거 모델 인용을 현재 법률 근거로 승격하지 않으며, source DTO와 카드 헤더의 모델 정보는 그대로 보존한다.

## 변경

- `SafeMarkdown`: 빈 줄, 설명 행, 들여쓴 하위 목록을 구조적으로 파싱해 하나의 ordered-list semantic tree로 렌더한다.
- 대화 상세 계약: `active_company_name`, turn `company_name`을 추가했다. `getCompanyById` 실패는 catch하여 owner-scoped conversation detail을 계속 반환한다.
- `ChatPanel`: 복원된 상세의 회사명을 사용한다. 현재 페이지 회사명은 동일 ID일 때만 사용한다. 과거 user turn은 그 turn의 회사명만 표시하고 raw ID를 표시하지 않는다.
- 답변 정제: provider 접두어와 history annotation을 Dual/Responses 결과, 저장, guest import, UI 렌더링 및 client recent history 경계에서 줄인다.
- Vitest 설정: 기존 `*.test.ts` 제한 때문에 `SafeMarkdown.test.tsx`가 실행 대상에서 빠져 있던 것을 `*.test.{ts,tsx}`로 고쳤다.

## 남은 문제와 후속 06 인계

1. 격리 PG16과 로그인 세션이 준비되면 브라우저에서 목록 렌더링, 회사 A→B 복원·전환·해제, 회사 조회 실패 시 복원 지속을 확인한다. 이후 새로고침/재로그인 복원은 후속 03의 실제 DB acceptance와 함께 확인한다.
2. provider header는 의도된 UI다. 본문 접두어가 실제 provider에서 다시 생성되지 않는지, Upstage/SKT/Responses 각각의 준비된 로컬 환경에서 합성 질문으로 확인한다.
3. 후속 06은 아직 남은 Stage 12의 **새 격리 PG16** 검증(마이그레이션/snapshot/권한/worker/summary retry/restart)을 시작점으로 삼는다. 운영·복원 DB는 사용하지 않는다.
