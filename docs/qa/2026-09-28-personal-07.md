# Money Worry 개인 후속 작업 07 — 운영 DB·대화 worker 인수

조사·격리 검증: 2026-09-29. 이 문서는 요청된 2026-09-28 파일명으로 기록한다.

## 판정

| 항목 | 로컬 코드·격리 검증 | 실제 운영 |
| --- | --- | --- |
| PG major·migration | 새 PG16.15, journal `0000`~`0020`, ledger 21, 후조건 115 aligned, replay no-op | 대상 DB·major·ledger·drift 미확인 |
| 기능별 권한 | `wg_auth`와 `wg_conversation` 분리, 대화 테이블 7개 CRUD·타 영역 차단 합성 검증 통과 | 실제 role 생성·grant 미확인 |
| 저장 모드 | real 모드의 합성 HTTP 저장·재로그인·재시작·복원 통과 | serving web 프로세스의 `CONVERSATION_DATA_MODE`, 전용 URL 미확인 |
| worker | 별도 Node 22 artifact 빌드, crash·lease·요약 재처리·동시 재시작 합성 검증 통과 | 설치 artifact·service/timer·최근 성공 실행 미확인 |
| backlog | 읽기 전용 집계 SQL 준비·새 DB에서 실행 통과 | 만료 대화·오래된 요약/요청 pending 개수 미확인 |

**코드·격리 준비 완료, 운영 적용·검증 미완료.** 로컬에서 프로세스가 존재하거나 소스에
`real` 옵션이 있다는 사실은 운영 DB 적용·저장 성공·worker 처리 성공을 증명하지 않는다.
이 환경에는 운영 VM 접속 대상/인증이 제공되지 않았고 `gcloud`와 `psql`도 없다.
Docker Engine은 로컬 격리 시험에만 접근했다. 운영 DB·서비스에는 연결하거나 변경하지 않았다.
이는 제품 결함이나 새로운 서비스 정책 결정으로 분류하지 않는다.

## 확인한 경로와 수정

- `infra/scripts/deploy-from-git.sh`는 migration을 **읽기 전용** 검사하고 새 SQL을 적용하지 않는다.
  웹 Next build도 대화 worker bundle을 만들지 않는다. 따라서 최신 웹 코드 배포와 worker 설치는
  각각 확인해야 한다. `infra/scripts/install-systemd-units.sh`는 DB/RAG/contract/web 4개 unit만
  설치한다. 대화 worker의 `.service.in`/`.timer`는 별도로 존재하며 timer는 부팅 2분 뒤,
  이후 30분 간격이다. unit 파일의 존재는 설치 증거가 아니다.
- `product/src/config/dataMode.ts`는 대화 모드를 `APP_DATA_MODE`에서 상속할 수 있지만,
  `product/src/server/databaseConfig.ts`의 대화 연결은 전용 `CONVERSATION_DATABASE_URL`이
  필요하다. 따라서 web env에 명시적으로 `CONVERSATION_DATA_MODE=real`과 전용 role URL을
  요구하도록 `infra/systemd/ENVIRONMENT_FILES.md`와 `infra/scripts/validate-service-envs.py`를
  고쳤다. URL은 owner/읽기 전용 bot/다른 쓰기 role이 아닌 `wg_conversation`이어야 한다.
- `db/scripts/run-conversation-pg16-acceptance.mjs`의 migration 재실행 검사가 과거 고정값
  20을 기대하던 오류를 현재 journal 길이 비교로 고쳤다. migration 정의나 ledger는 수정하지 않았다.
- 기존 운영 `db.env`는 앱 role 비밀번호를 담지 않는데 `create-conversation-role.sh`는 이를
  기대했다. 운영자만 읽는 별도 `CONVERSATION_PASSWORD_FILE`(root 소유, 0600 이하)을
  허용했다. 비밀번호를 DB 서비스 env 또는 명령행에 추가하지 않는다.
- `db/scripts/conversation-ops-readonly.sql`을 추가해 대상 DB/major, role·7개 테이블 권한,
  타 영역 접근, 만료 backlog, 오래된 요약·요청 pending을 **집계값만** 확인할 수 있게 했다.
  ID, 본문, payload, URL, 비밀번호는 조회하지 않는다.
- `infra/scripts/render-conversation-maintenance.py`는 별도 worker service/timer를 명시된
  경로·계정으로 렌더링만 한다. 설치·daemon reload·start는 수행하지 않는다.
- `db/docs/MIGRATION_OPERATIONS.md`의 2026-09-14 운영 ledger 설명을 과거 스냅샷으로
  표시하고, 현재 로컬 journal과 운영 미확인 상태를 구분했다.

## 운영 읽기 전용 확인 — 계정 소유자 실행

OS Login으로 실제 운영 VM에 접속한 뒤, 대상이
`/srv/moneyworry/repo/2nd_Side2026_Project`의 서비스인지 먼저 확인한다. 다음은 상태를
바꾸지 않는다. **URL·env 원문·로그 원문은 회신하지 않는다.** 명령 실패와 집계·해시만
비밀값을 제거해 회신한다.

```bash
cd /srv/moneyworry/repo/2nd_Side2026_Project
sudo systemctl show moneyworry-web.service -p ActiveState -p MainPID -p ExecMainStartTimestamp -p WorkingDirectory -p ExecStart --no-pager
sudo systemctl show moneyworry-conversation-maintenance.service moneyworry-conversation-maintenance.timer -p LoadState -p ActiveState -p Result -p LastTriggerUSec -p NextElapseUSecRealtime --no-pager
sudo systemctl list-timers moneyworry-conversation-maintenance.timer --all --no-pager
sudo test -f product/.next/BUILD_ID && sudo cat product/.next/BUILD_ID
sudo test -f product/.runtime/conversation-worker.mjs && sudo sha256sum product/.runtime/conversation-worker.mjs
sudo sh -c 'cd db && npm run --silent check:migration-drift -- --env-file /etc/moneyworry/db.env --json'
```

`web.env`는 다음 명령이 **모드와 URL의 비밀 아닌 구성 요소만** 출력한다. 전체 env를
`cat`, `systemctl show -p Environment`, 셸 `source`로 노출하지 않는다.

```bash
sudo python3 - <<'PY'
from pathlib import Path
from urllib.parse import urlsplit, unquote
values = dict(line.split('=', 1) for line in Path('/etc/moneyworry/web.env').read_text().splitlines()
              if '=' in line and not line.lstrip().startswith('#'))
for key in ('APP_DATA_MODE', 'CONVERSATION_DATA_MODE'):
    print(key, values.get(key, '<absent>'))
url = values.get('CONVERSATION_DATABASE_URL', '')
p = urlsplit(url)
print('CONVERSATION_DATABASE_URL',
      'absent' if not url else (unquote(p.username or ''), p.hostname, p.port, p.path, p.scheme))
PY
```

운영 코드에 이 작업의 SQL이 반영된 뒤에만 아래 집계를 실행한다. `psql`이 호스트에 없어도
기존 DB 컨테이너의 client를 사용한다. `db.env`는 compose가 직접 읽으며 값이 출력되지 않는다.
실행 전에 `docker compose ... ps db`로 **올바른 운영 프로젝트**인지 확인한다.

```bash
sudo docker compose --env-file /etc/moneyworry/db.env -f db/docker-compose.yml ps db
sudo docker compose --env-file /etc/moneyworry/db.env -f db/docker-compose.yml exec -T db sh -c 'exec psql -X -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < db/scripts/conversation-ops-readonly.sql
sudo journalctl -u moneyworry-conversation-maintenance.service --since '24 hours ago' --no-pager -o cat
```

마지막 journal은 `version`, `deleted`, `candidates`, `summarized`, `failed`, exit status와
실행 시각만 회신한다. 전체 로그에 예기치 않은 비밀값이 있으면 먼저 제거한다. timer가 active라도
최근 oneshot exit가 성공이고 backlog가 줄지 않았다면 처리 성공으로 판정하지 않는다.

## 조건부 운영 적용 패키지 — 아직 실행하지 않음

**대상:** 위 읽기 전용 결과가 가리키는 단일 운영 VM, 단일 운영 PG16 DB, 해당 웹 서비스 및
대화 maintenance service/timer. 배포 대상의 승인된 40자리 source SHA, 현재 웹 BUILD_ID,
기존 worker 해시와 기존 unit 상태를 적용 기록에 묶는다. 현재 운영 SHA/ledger/role/unit이
확인되지 않았으므로 아래 절차는 준비안이며 변경 실행 승인은 아직 요청하지 않는다.

1. **중단 gate.** 대상 VM·DB 이름/major/서비스 경로·배포 source SHA를 특정한다.
   `check:migration-drift`가 `diverged`, `partial`, `schema_ahead`, 접속 오류이면 중단하고
   [migration 복구 절차](../../db/docs/MIGRATION_OPERATIONS.md)를 따른다. pending SQL의
   실제 목록 없이 `npm run migrate`를 실행하지 않는다. custom-format dump의 SHA-256,
   격리 복원 성공과 외부 비공개 보관을 확인한다. 이전 web env/unit/worker bundle과 각 해시를
   보존한다. 운영 DB·권한·env·service 변경은 **각 변경과 대상 승인 후에만** 실행한다.
2. **migration이 pending일 때만:** 승인된 SQL 목록·순서를 확정하고 웹 쓰기를 멈춘 뒤
   [운영 migration 절차](../../db/docs/MIGRATION_OPERATIONS.md)로 적용한다. ledger를 직접
   편집하거나 과거 migration을 다시 실행하지 않는다. 직후 같은 read-only drift가 `aligned`,
   ledger 21, 후조건 115인지 확인한다. 이미 aligned면 이 단계를 생략한다.
3. **role이 부족할 때만:** migration 완료 후 아래 명령을 승인된 운영자 계정에서
   실행한다. `psql` PG16 client가 호스트에 없다면 먼저 중단하고 설치 방식을 확인한다.
   `/etc/moneyworry/conversation-role.secret`은 root 소유 `0600` 한 줄 비밀번호 파일로
   운영자가 로컬에서 준비하며 web/worker URL의 인코딩 전 값과 일치해야 한다. 파일 값은
   채팅/명령행에 쓰지 않는다. 이 스크립트는 `wg_conversation` 비밀번호와 grant를 갱신한다.

   ```bash
   sudo stat -c '%U %a %n' /etc/moneyworry/conversation-role.secret
   sudo env DB_ENV_FILE=/etc/moneyworry/db.env \
     CONVERSATION_PASSWORD_FILE=/etc/moneyworry/conversation-role.secret \
     bash db/scripts/create-conversation-role.sh
   ```

   `wg_auth`도 부족할 때만 해당 role 절차를 별도로 검토한다. 위 집계 SQL과 서비스
   로그인으로 전용 권한과 타 영역 차단을 재확인한다.
4. **web env가 부족할 때만:** 기존 `web.env` 백업·비밀 아닌 해시를 보존하고, root 전용
   임시 파일에 `CONVERSATION_DATA_MODE=real` 및 `wg_conversation@127.0.0.1:5433/wageguard`
   전용 URL을 포함한다. 비밀번호를 명령행/채팅/로그에 쓰지 않는다. 다음 검증 후 원자적으로
   교체하고 승인된 웹 재시작을 한다. 기존 네 서비스의 다른 값은 유지한다.

   ```bash
   sudo python3 infra/scripts/validate-service-envs.py --db-env /etc/moneyworry/db.env --web-env /etc/moneyworry/web.env --rag-env /etc/moneyworry/rag.env --contract-env /etc/moneyworry/contract.env
   ```

   교체 **전**에는 이 명령을 root 전용 임시 web env 경로로 실행한다. `validated split service
   environment contracts` 외의 결과나 서비스 503이면 중단한다.
5. **worker가 없거나 구버전일 때만:** 승인된 source SHA가 설치된 코드에서 Node 22로
   `cd product && npm ci && npm run worker:conversation:build`를 실행한다. 산출물
   `.runtime/conversation-worker.mjs`의 SHA-256을 기록하고 웹 서비스 계정이 읽을 수 있는지
   확인한다. 전용 `/etc/moneyworry/conversation-worker.env`는 root 전용이며
   `CONVERSATION_DATABASE_URL`과 `DB_SSL`만 담는다. `@PROJECT_ROOT@`, `@WEB_SERVICE_USER@`,
   `@WEB_SERVICE_GROUP@`, `@NODE_BIN@`, `@CONVERSATION_WORKER_ENV_FILE@`을 기존
   `.service.in`에 정확히 치환하고 timer와 함께 `systemd-analyze verify`한다. 설치 대상은
   `/etc/systemd/system/moneyworry-conversation-maintenance.{service,timer}`다.
   승인된 설치 후 `systemctl daemon-reload`, oneshot 1회, exit/log/backlog 확인,
   `systemctl enable --now moneyworry-conversation-maintenance.timer` 순서로 적용한다.
   기존 설치본이 정상·동일하면 재설치/재시작하지 않는다.

   아래 명령은 **승인 후**, 실제 web unit의 User/Group/WorkingDirectory가 확인되고 전용
   env가 root 소유 `0600`, 실제 Node가 v22이며 worker artifact가 빌드됐을 때에만 실행한다.
   먼저 새 render 디렉터리에서 unit을 검증한다. 대상 unit이 이미 다른 내용이면 덮어쓰기
   전에 이전 파일을 보존한다.

   ```bash
   cd /srv/moneyworry/repo/2nd_Side2026_Project
   WEB_USER=$(systemctl show moneyworry-web.service -p User --value)
   WEB_GROUP=$(systemctl show moneyworry-web.service -p Group --value)
   NODE_BIN=$(readlink -f "$(command -v node)")
   test -n "$WEB_USER" && test -n "$WEB_GROUP" && "$NODE_BIN" --version
   sudo stat -c '%U %a %n' /etc/moneyworry/conversation-worker.env
   render_dir=$(sudo mktemp -d /run/moneyworry-conversation.XXXXXXXX)
   sudo python3 infra/scripts/render-conversation-maintenance.py \
     --project-root /srv/moneyworry/repo/2nd_Side2026_Project \
     --web-user "$WEB_USER" --web-group "$WEB_GROUP" \
     --node-bin "$NODE_BIN" \
     --worker-env-file /etc/moneyworry/conversation-worker.env \
     --output-dir "$render_dir"
   sudo systemd-analyze verify "$render_dir"/moneyworry-conversation-maintenance.service "$render_dir"/moneyworry-conversation-maintenance.timer
   sudo install -o root -g root -m 0644 "$render_dir"/moneyworry-conversation-maintenance.service /etc/systemd/system/moneyworry-conversation-maintenance.service
   sudo install -o root -g root -m 0644 "$render_dir"/moneyworry-conversation-maintenance.timer /etc/systemd/system/moneyworry-conversation-maintenance.timer
   sudo systemctl daemon-reload
   sudo systemctl start moneyworry-conversation-maintenance.service
   sudo systemctl show moneyworry-conversation-maintenance.service -p Result -p ExecMainStatus --no-pager
   sudo systemctl enable --now moneyworry-conversation-maintenance.timer
   sudo systemctl list-timers moneyworry-conversation-maintenance.timer --all --no-pager
   ```

   `Result=success`/`ExecMainStatus=0` 및 backlog 감소를 확인하기 전에는 timer를 enable하지
   않는다. Node가 v22가 아니거나 출력된 `NODE_BIN`이 실제 binary가 아니면 중단한다.
   기존 unit이 있을 때에는 교체 전 보존 파일·해시를 기록한다.
6. **smoke:** `systemctl is-active moneyworry-web`, Node/BUILD_ID와 worker hash/oneshot
   version 대조, 실제 승인된 합성 계정의 로그인→대화 저장→재로그인/웹 재시작 후 조회,
   요약 checkpoint 재처리, 만료·pending 집계 감소, timer 다음 실행 시각을 확인한다.
   대화 본문/계정 ID는 기록하지 않는다. 서비스 저장 성공과 worker 성공을 각각 판정한다.

**복구:** 오류가 나면 timer를 중지하고 새 oneshot을 시작하지 않는다. 이전 web env/unit/worker
artifact를 보존본으로 되돌리고 `daemon-reload` 후 이전 웹 서비스 설정을 복원한다. 새 migration
또는 ledger를 임의로 되돌리거나 DB를 초기화하지 않는다. 이미 적용한 migration에 문제가 있으면
승인된 dump·격리 복원 결과에 기반한 별도 DB 복구 결정을 한다. rollback 뒤 로그인·읽기와
기존 저장 기능을 smoke하고 backlog를 읽기 전용으로 다시 집계한다.
