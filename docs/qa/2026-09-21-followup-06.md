## 2. 확인된 원인과 수정

### Snapshot 정합성

- 시작 schema에는 이미 conversation 7개 테이블, SQL/journal은 0017까지 있었다. 0014~0017 snapshot은 없었다. PR #115의 0018 snapshot은 0013을 prevId로 가지고 conversation 7개가 전부 빠진 상태였다.
- 운영 자료의 **0017까지 적용됐다는 과거 기록**과 snapshot 누락은 독립 문제다. 이번에 운영 ledger를 조회하거나 변경하지 않았다.
- 0018 SQL은 PR 병합본과 바이트 동일하게 반영. 그 누적 snapshot에 이미 구현된 7개 테이블 정의만 보강했다. 기존 0014~0017 SQL, 기존 journal 시각을 수정하지 않았고 빈 migration/중복 CREATE로 ledger를 맞추지 않았다. 0014~0017 번호별 가짜 snapshot도 만들지 않았다.
- 복구 baseline에서 Drizzle generate 결과는 정상적으로 추가 SQL 0개였다. 이후 lease 컬럼을 schema에 추가하여 **실제 Drizzle generate로** `0019_conversation_summary_leases.sql` 및 snapshot 생성: `ALTER TABLE conversation_summaries ADD COLUMN` 두 문장뿐, 기존 테이블 CREATE 없음. 최종 재생성도 SQL 0개.

### 실제 DB에서 드러난 요약·저장 결함

1. **정상 upsert 차단**: 공통 쓰기 SQL 검사기가 `DO`를 무조건 금지하여 `claimSummary`의 `ON CONFLICT … DO UPDATE`를 차단했다. Mock 요약 테스트는 이를 지나지 않았다. 새 PG16에서 실제 실패 재현 후 upsert의 DO만 허용; DDL, 익명 DO block, 여러 문장 및 뒤따르는 DROP은 계속 차단한다. 이 사실만으로 과거 운영 QA의 특정 summary 행 상태를 확정하지 않는다.
2. **stale pending 영구 잠금**: 기존 summary claim은 pending이 남으면 회수할 수 없었다. nullable token/expiry, 120초 lease, 30초 heartbeat, DB 시각 기준 원자적 회수 추가. token+target+expiry로 complete/fail/renew를 제한하여 이전 작업이 새 요약을 덮지 못한다. claim 후 완료 checkpoint를 다시 읽는다. legacy pending은 updated_at+120초 기준 회수.
3. **만료 응답 replay**: request 재사용 경로가 만료된 thread를 검사하지 않았다. claim/complete에 소유자·유효기간·명시적 conversation 일치 검사를 추가했다. complete는 parent→request 잠금 순서로 삭제 cascade와 맞춘다.
4. **연결급 SQLSTATE 분류**: `080xx`, `57P01/02/03`도 일반 SQL 오류로 전달되어 HTTP save-retry 분기를 놓칠 수 있었다. retryable 503으로 분리했다. 제약 오류는 그대로 유지하며 기존 COMMIT 결과 불명확 처리도 유지한다. 실제 PG에 합성 `08006` trigger를 걸어 HTTP 저장 롤백→생성 결과 캐시→동일 request 저장만 재시도 경로를 검증했다.

### Worker 연결

- `conversationMaintenanceService` + standalone Node worker + 빌드 명령 + systemd oneshot/timer **템플릿** 추가. 기존 purge 함수를 실제 실행 가능한 worker 경로에 연결했다. 운영 설치는 하지 않았다.
- 한 pass: 만료 100개 `SKIP LOCKED` cascade 삭제, 요약 후보 25개. failed는 60초 후, stale pending은 lease 만료 후 재시도하므로 신규 질문을 기다리지 않는다. 중복 프로세스·재시작 안전성을 실제 PG에서 검사했다.
- 로그는 상태/개수/버전만. DB/요약 실패 시 nonzero. worker는 Mock 실행을 거부하고, 실제 검사 때 auth/owner URL 없이 `wg_conversation`으로 실행했다.
- 역할 스크립트의 비밀번호 argv 전달을 환경변수+psql `\getenv`로 교체했다. 운영 예제에 비밀값을 기록하지 않았다.
- 생성 번들용 esbuild는 현재 설치 버전 `0.28.1`을 직접 dev dependency로 고정했다. `.runtime` 생성 번들은 Git/ESLint 제외이고 원본 scripts는 계속 lint/typecheck한다.

1. 상담 원문·요약·완료 응답 중복의 목적 및 최소 저장 범위, 고지/동의 UX, 암호화·접근감사 책임.
2. 상담 외 이벤트를 정말 수집할 기능과 필드 allowlist, 기존 회사 event/관심 테이블 참조로 충분한 범위, 추가 저장의 필요성.
3. 현재 활동 기준 30일과 초안 90/30일의 적용 대상, 기준 시각, 물리 삭제 지연/backup 잔존 기간, 백업 복구 후 삭제 재적용 방식.
4. 외부 LLM 전송 승인 대상(특히 감독관 값)·공급자/상담 범위·TTL·철회 즉시 효력·이미 전송한 자료의 처리. import 동의로 대체할 수 없음.
5. 사용자 탈퇴가 물리 삭제인지, 커뮤니티/파일/관심/동의까지 함께 지울지 또는 예외를 둘지. 이번 실측은 physical users delete의 기존 FK cascade만 보장.
6. 실행 중 **chat request**가 앱 crash로 pending에 남았을 때 만료/실패 전환 및 사용자 재시도 UX. 완료 replay와 저장 전 5분 메모리 캐시는 구현됐지만 crash-durable generated-response 저장이나 자동 재생성은 구현하지 않음.

### 나연에게 전달할 문안 — 작성만, 전송하지 않음

> PR #115의 user_favorite_firms/role/drift를 확인했고 로컬 작업 6 기준에 반영했습니다. 대화 7개 테이블이 빠진 0018 누적 snapshot은 메타데이터로 보강했으며, 기적용 0014~0017과 병합된 0018 SQL은 수정하지 않았습니다. 새 0019는 summary lease 두 컬럼만 추가하고, 빈 PG16 전체 적용·111개 후조건·재생성 SQL 0개를 확인했습니다. 기존 conversation_*는 상담 원문/요약/요청 재사용을 담당하므로 초안 두 테이블과 중복 구현하지 않았습니다. 교차 기능 이벤트 수집 대상, 30/90일 기준·삭제/backup, 원문 저장 고지·보호, 감독관 외부 전송 승인 범위/TTL/철회, 탈퇴 범위를 구분해 결정 부탁드립니다. 관심 상태는 favorites를 원본으로 두고 이벤트 이력 추가 필요성도 확인 부탁드립니다. 실제 운영 적용 번호/백업/role/worker 설치는 별도 승인 절차로 진행해야 합니다.

후속 7 시작점:

1. 사용자 Git 작업 후 최신 main/PR115와의 최종 이력/파일 통합을 재확인한다. 0018 SQL 바이트 및 **복구된** snapshot을 유지하고 다른 최신 0019 번호 충돌이 없는지 확인한다. Git 작업은 계속 사용자가 담당한다.
