## 검색 정책

- 산재보험을 범위 안으로 옮겼다. `산업재해·산업안전` 범위 밖 주제에서 산재보험·근로복지공단·산재 신청 키워드를 뺐다. 산업안전보건법·중대재해·안전관리자·작업중지·안전조치는 계속 막는다.
- 연말정산을 막는다. 새 주제 `연말정산`을 두었다. 수록 뒤 "연말정산 환급금은 언제 들어오나요?"가 산재보험법 제70조(거리 0.411)로 새어 나가 16건 negative 가운데 한 건이 실패했기 때문이다.
- 4대보험은 둘로 나눴다. 외국인 건강보험 질문만 통과시킨다(외국인고용법 제14조). 국민연금·4대보험 질문은 외국인이 언급돼도 계속 막는다.
- 새 두 법의 조문은 질문에 그 맥락이 있을 때만 먼저 고른다.
  - 맥락 판정: 산재보험법은 산재·업무상·부상·요양·근로복지공단 등, 외국인고용법은 외국인·E-9·비자·고용허가·사업장 변경 등의 말이 있어야 한다.
  - 맥락이 없으면 빈자리만 채운다. 기존 특례 조문 규칙과 같은 방식이다.
  - 이 규칙이 없을 때는 "상시 사용하는 근로자 수는 어떻게 계산하나요?"의 1위가 산재 시행령 제2조의2로 바뀌어 HB top-1이 71에서 70으로 떨어졌다. "휴업수당" 질문의 상위 5건에도 산재 휴업급여 3건이 끼었다.
- 질의 확장 규칙:
  - 산재 신청과 산재 인정은 규칙을 나눴다(제41·36조 / 제37조). 초안은 "산재가 되나요?"도 신청 조문으로 확장해 우울증 산재 질문이 빗나갔다.
  - 산재 급여별 규칙(장해·유족·심사청구)은 산재 맥락이 있을 때만 붙인다.
  - 외국인 맥락과 산재 맥락이 함께 있으면 적용 범위 조문(제6·5조)을 붙인다. 체류자격과 관계없는 산재 적용 질문이 여기에 해당한다.
  - 5명 미만 농업·임업·어업은 시행령 제2조로 확장한다.
  - 사업장 변경은 제25조, 출국만기·퇴직금은 외국인 맥락일 때 제13조, 차별은 제22조, 최저임금은 외국인 맥락일 때 최저임금법 제6조로 확장한다. "회사를 옮기다·이직" 같은 일반 표현은 외국인 맥락이 있을 때만 제25조로 확장한다.
- 거리 임계값 0.42와 강한 일치 0.30은 그대로다. 임계값을 바꿀 근거는 없었다. 새 질문의 정답 조문은 모두 0.42 안에 들어왔다.

## 제품(TS) 경로

초안은 가드레일 법령 목록과 약칭만 바꿨다. 이번에 산재·외국인고용 질문이 RAG에 닿지 못하던 경로를 추가로 고쳤다.

- `reviewedLaborGuidance`: "요양급여·휴업급여·유족급여"의 "급여"가 임금 번들을 발동시켰다. 그래서 퇴직·사망 지급, 진정 접수, 사업주 확인서 번들이 산재·외국인 질문을 가로채 HTTP RAG를 부르지 않았다. 새 주제에서는 번들을 쓰지 않는다.
- `answerPlanService`: 의도 분류가 unclear/company여도 산재·외국인고용 고유 절차를 물으면 노동 RAG 경로로 보낸다. 회사 "산업재해 카드·지표" 질문과 전세보증보험 같은 일반 보험 질문은 제외한다.
- `MockChatProvider` 응급 분기: "지난달 일하다 다쳤는데 산재 되나요?", "사고 났는데 휴업급여" 같은 사후 급여 질문이 응급 안내로 끝나던 문제를 고쳤다. 급성 부상 문장은 계속 응급으로 먼저 처리한다.
- `guardrails`: "근로복지공단에 신청하세요(「산업재해보상보험법」 제41조)"처럼 기관명 뒤에 「수록 법령명」이 오면 지어낸 안내 문서로 판정해 답변을 교체하던 문제를 고쳤다. 수록되지 않은 법과 지어낸 문서명은 계속 막는다.

## 배포 절차 (관문 경로 승인 필요)

바뀐 관문 경로는 `infra/systemd/`와 `product/integrations/rag-api/config/`다. 운영 RAG는 저장소의 `data/labor_law_db`가 아니라 `/srv/moneyworry/rag-db`의 봉인본을 읽는다. 따라서 코드 배포만으로는 부팅이 실패한다. 새 manifest와 옛 DB·seal이 서로 맞지 않기 때문이다. 아래 순서를 지킨다.

1. 새 커밋을 체크아웃한 뒤 저장소의 `data/labor_law_db`(5개 파일)를 `/srv/moneyworry/rag-db`로 교체한다. 기존 본은 백업한다. 소유와 권한은 README 절차(root:`<RAG_GROUP>`, u=rwX,g=rX,o=)를 따른다.
2. `prepare_rag_assets.py prepare --manifest …/config/rag_assets.v1.json --hf-home /srv/moneyworry/hf --rag-db /srv/moneyworry/rag-db --confirm PREPARE_BAAI_BGE_M3_5617A9F6`를 실행한다. 모델 파일은 그대로 쓰고 seal의 manifest hash와 문서 수만 새로 기록한다.
3. `install-systemd-units.sh --force`를 실행한다. unit의 `RAG_EXPECTED_DOCUMENT_COUNT=806`을 반영해야 하기 때문이다.
4. `deploy --ack-guarded infra/systemd/ --ack-guarded product/integrations/rag-api/config/`를 실행한 뒤 콘솔에서 "고정 질의 호환성을 검증했습니다"와 `/api/health/ready`를 확인한다.

systemd 변경이 꼭 필요한 이유는 다음과 같다. unit이 `RAG_EXPECTED_DOCUMENT_COUNT`를 고정하고, `retriever._validate_runtime_contract`는 이 값이 manifest 문서 수와 다르면 부팅을 거부한다. 메모리나 시작 시간 때문은 아니다. 223건이 늘어도 영향은 무시할 수준이고, `TimeoutStartSec=15min`도 그대로다.

## 남은 위험

- 서버(linux/amd64) 부팅을 직접 실행하지는 못했다. 대신 다음 사실로 통과를 판단했다.
  - 고정 질의는 `kis_a43` 원문을 질의로 넣어 같은 문서가 거리 1e−4 이하로 1위에 오는지 본다.
  - 이 문서의 저장 벡터는 현재 운영 번들과 비트 단위로 같다.
  - 질의 임베딩의 플랫폼 차이는 이 Mac에서 약 1e−7이었다.
  - DB 파일은 같은 chromadb 1.5.9 SQLite 형식이다.
