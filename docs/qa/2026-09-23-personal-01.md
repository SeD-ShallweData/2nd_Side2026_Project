## 3. 현재 질문→답변→기억 흐름

1. `app/api/chat/route.ts`: same-origin·요청 형식·세션·익명 quota·외부 AI 동의 검사. raw parser는 클라이언트가 주입한 memory/recall을 신뢰하지 않는다.
2. 로그인 요청은 `conversationService`에서 owner-scoped request claim/replay 후 **생성 전에** DB detail·완료 summary·recent originals·company events/회상 사실을 hydrate한다. 이미 완료된 요청이면 저장 응답을 재사용한다. DB503 때 다른 방 client history로 대체하지 않고 기억을 비운다.
3. `chatExecutionService`가 `dual_api`와 `openai_responses`를 선택한다. `dual_api`라는 설정 이름만으로 항상 두 공급자를 호출하는 것은 아니다. UI compare 기본 false이며 일반 요청은 Upstage 하나, compare=true일 때 Upstage+SKT를 같은 준비 context로 호출한다. 별도 비교 동의를 요구한다.
4. `chatComparisonService`: policy baseline/긴급 분기 → **사용자 진술 회상 short circuit** → 후속 재작성 → intent/AnswerPlan → 필요한 노동 검색 또는 company context → reviewed applicability 근거 보강 → 최종 생성 context. 회상은 검색/생성 없이 반환할 수 있다.
5. 노동 RAG와 공개 회사 DTO는 서로 다른 근거다. summary는 재작성·분류·생성에 참고 진술로 전달되며 현재 법률/회사 사실의 근거가 되지 않는다. 현재 회사와 턴 당시 회사 관계도 분리한다.
6. `DualLlmChatProvider`에서 생성 → 공개 텍스트 정리 → guardrail scan → 원시 답변 유지/관련 근거를 보존한 교체. API 장애면 policy fallback이다. provider HTTP 실패도 앱 HTTP200/최종 계약 PASS가 될 수 있으므로 세 지표를 분리해야 한다.
7. 최종 표시 답변·sources를 transaction/request fencing 경계로 저장한다. 저장503에는 5분 process-local 생성 캐시로 저장만 재시도할 수 있지만 app crash 뒤 그 캐시를 보장하지 않는다. 완료 ledger replay는 DB에 남는다.
8. 10개 완료 메시지 단위 `extractive-v2` summary/최대10 recent originals, 실패·stale lease를 회수하는 maintenance worker가 구현돼 있다. 요약은 별도 LLM 호출이 아닌 추출 방식이다. UI의 list/detail/restore/import/delete가 저장된 최종 답변과 회사 표시명을 복원한다.

현재 제품의 주력은 일반 Upstage 경로로 읽힌다. SKT는 비교 경로이지 이번에 검증한 자동 장애 대체 공급자가 아니다. Responses는 설정 선택 경로로 코드/공유 기억·가드가 존재하나 이번 live는 NOT RUN. 실제 운영의 선택 모드·키 유효성·비교 활성은 미확인이다.
