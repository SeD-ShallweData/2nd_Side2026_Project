### 원문 생성 오류와 과잉 차단 구분

합성 provider transport로 실제 Dual 가드레일 구현을 실행했다.

- “급여일 15일, 다음 주 지급이라고 말씀하셨다”는 정상 회상 문장: `success`, 인용 규칙 hit 없음.
- 같은 문장에 현재 검색 문서에 없는 `근로기준법 제999조`를 추가: `UNVERIFIED_LAW_CITATION`, `guardrail_replaced`. 이는 합성된 원문 생성 오류이며 정상 차단이다.
- 두 경우 및 Responses의 잘못된 인용 대체에서도 최종 혼합 답변에는 사용자 진술 15일·다음 주가 남고 잘못된 조문은 남지 않는다.

수동 QA 당시 원문/trace hit가 없으므로 당시 차단이 같은 규칙인지, 다른 규칙인지, 과잉 차단인지 **미확인**이다. `matched`만으로 법률 정확성을 선언하지 않았다.

## 구현 세부와 안전 경계

1. `conversationRecallService`는 급여일/회사 지급 약속의 **제한된 사실 회상**을 담당한다. 날짜 변경(7→21, 25→5 포함), 정정, 약속 철회, 부정, 정보 없음, 질문/가정·다른 사람 진술 제외를 검사했다. 사용자 입력 전체를 출력하지 않고 정규화한 날짜/시점만 사용한다. 상대 표현 “다음 주”는 당시 표현임을 명시한다.
2. summary의 `recall_facts`는 원문 메시지 ID·순서·당시 회사·정정 여부를 가진다. 최대 64개를 저장하며 이전 값과 정정을 보존한다. 원문/과거 turn을 수정하지 않는다. 새 summary checkpoint에서는 보존 원문에서 재구성하므로 기존 필드 6개 제한으로 날짜/약속이 밀려나지 않는다.
3. v1 summary가 있는 상담도 owner 확인한 저장 원문으로 회상 슬롯을 **메모리에서** 재구성한다. 조회 시 DB summary를 쓰거나 마이그레이션하지 않는다. 다음 정상 요약 갱신 때 v2가 기록된다.
4. hydration은 완료 prefix의 summary 슬롯과 이후 사용자 원문을 결합한다. 현재 회사 A/B/미선택과 정확히 일치하는 진술만 회상한다. B의 약속이 없으면 A의 약속을 옮겨 쓰지 않고, 회사 해제 후 A/B 값을 현재 값이라고 말하지 않는다. 다시 A로 선택하면 A의 기록은 남아 있다.
5. 기존 raw `parseChatRequest` allowlist가 `conversation_memory`와 새 `conversation_recall`을 모두 버린다. 로그인 요청은 owner 확인한 저장 원문으로 클라이언트 이력을 대체한다. claim/hydration이 503이면 클라이언트 이력으로 몰래 되돌아가지 않도록 비운다. 같은 사용자 다른 방·다른 owner·주입한 29일·assistant의 28일은 회상값에 섞이지 않는 회귀를 추가했다.
6. `trace.memory`는 summary 상태/버전, 완료 지점, 저장 메시지 수, hydrated 최근 수, 포함 여부, 회상 슬롯 수, legacy 재구성 여부뿐이다. 공개 trace에는 요약 본문·원문 ID·회사별 슬롯·개인정보·시스템 프롬프트를 넣지 않는다. 새 일반 로그 출력도 없다. 회상 경로는 `recall_mode`와 검색 미호출 reason을 명시하고 실제 모델을 호출한 것처럼 기록하지 않는다.
7. 법률/혼합 질문은 검색·생성·기존 가드레일을 거친다. 혼합 질문의 회상 부분과 추가 안내를 구분한다. emergency 우선순위와 Responses 계약서 업로드 도구 경로도 유지한다. 모든 정상 질문을 회상 fallback으로 바꾸지 않았다.

범위 제한: 임의의 모든 과거 사실을 추출하는 범용 메모리 시스템이 아니다. 지원하지 않는 표현·복잡한 중복 날짜·한도 밖 오래된 사실의 완전한 회상은 보장하지 않는다. 해당 슬롯을 확인하지 못하면 추측하지 않는다. “다른 회사의 과거 사실을 명시적으로 지정해 회상”하는 별도 라우팅과 익명 클라이언트 이력의 진실성 보장은 이번 범위 밖이다.

## 연속 대화 실행기

기존의 최대 3개 step 제한은 “같은 사례 최대 3회 반복”과 “한 상담의 서로 다른 질문 수”를 혼동하므로, 최대 12개의 서로 다른 turn을 허용하도록 수정했다. 고정 corpus는 6개 질문+재로그인 후 회상 1개이며 반복 루프는 없다.

- 새 격리 PG16 대상임을 운영자가 확인하고 `ANSWER_EVAL_ISOLATED_PG16=1`을 설정해야 실행한다. 이 플래그 자체가 격리 증명은 아니다.
- session cookie는 메모리에만 유지한다. 매 요청은 `recent_messages: []`이고 반환된 conversation ID를 이어 쓴다. 각 turn은 `source: database`인 detail의 실제 질문·최종 답변과 대조한다.
- 7번 전에 새 로그인과 detail 복원을 수행한 뒤 같은 ID로 질문한다. 마지막에도 재로그인/detail을 확인한다. 브라우저 클릭이나 프로세스 재시작 검사는 아니다.
- 상태·개수·버전 allowlist만 결과에 복사한다. 후속 요청 실패 시 앞선 완료 행을 보존한다. HTTP 오류의 원문 message는 자격증명 반사 가능성 때문에 복사하지 않는다.
- request blocker는 `NOT_EVALUATED`, exit 2. 답변 계약 FAIL은 exit 1. Mock 응답으로 chaining/복원 순서·비밀 미기록·부분 결과 보존을 확인했지만 실제 DB 실행으로 집계하지 않는다.

## BLOCKED 항목 재개 절차

1. Docker Desktop Engine과 **새 빈 PG16**을 준비한다. 기존 restored/GCP/운영 DB는 사용하지 않는다. 앱 연결 대상과 auth/conversation 쓰기 role이 격리 DB를 가리키는지 비밀값을 출력하지 않고 확인한다.
2. 기존 `db/docs/MIGRATION_OPERATIONS.md`와 후속 01/AGENTS의 격리 acceptance 절차로 migration/role을 준비한다. 이번 변경 자체는 새 migration이 없다. 자동으로 운영 대상에 migrate하지 않는다.
3. 격리 DB에만 로컬 테스트 계정을 준비한다. 로그인/대화 저장은 real 모드로, 회사 데이터는 필요한 테스트 fixture로 실행한다. `ANSWER_EVAL_EMAIL`/`ANSWER_EVAL_PASSWORD`는 로컬 비공개 입력으로 현재 프로세스 환경에만 넣고 파일·스크립트 인자·콘솔에 남기지 않는다. 대상 확인 후에만 `ANSWER_EVAL_ISOLATED_PG16=1`.
4. 위 `eval:conversation-continuity`를 1회 실행한다. 4번은 stored 6/summary absent, 6번은 stored 10/ready/checkpoint 10/summary included, 7번은 stored 12/checkpoint 10/recent 2를 기대하되 실제 row/status를 직접 확인한다. 다른 수치가 나오면 곧바로 summary 실패로 단정하지 말고 완료 지점·상태·원문 수와 대조한다.
5. 같은 계정의 다른 방과 별도 계정, A→B→해제, 새로고침·다른 방 이동·재로그인 복원 및 앱 재시작을 별도로 검사한다. 브라우저 E2E와 서버 재시작 결과를 HTTP runner와 구분한다. 실제 provider는 필요한 합성 질문에 한해 사례당 최대 3회, 새 근거 없이 반복하지 않는다.
6. stale pending summary 재수거, worker/expiry, real role/late write/restart acceptance는 후속 06의 미완료 항목과 함께 검증한다. 이번 회상 수정이 이를 완료한 것은 아니다.

## 후속 04 인계

다음은 **RAG 품질**이다. 회상 실패를 고치기 위해 모든 회상 질문에 법령 검색을 강제하지 않는다.

1. 작업 2에서 남은 일반 노동 질문의 `service_unavailable`/거리 threshold/no_match, matched 후 부적합 문서를 분리해서 재현한다. `intent_short_circuit`, 이번 `conversation_recall_no_retrieval`은 검색 서비스 장애와 구분한다.
2. 현재 공식 근거의 적용 조건과 검색 문서의 조건 보존을 대조한다. 작업 2의 reviewed applicability bundle을 무작정 대체하지 않는다. 법률/회사 지표 계약과 새 AQ11/AQ23/AQ24를 함께 회귀한다.
3. 검색 성공/가드레일 통과/문자열 PASS를 최종 답변 정확성과 동일시하지 않는다. raw 생성, 실제 차단 규칙, 최종 답변 목적 유지 여부를 별도로 평가한다.
4. 위 Real DB·로그인·브라우저·재시작 BLOCKED와 작업 1의 공개 정책 미확정 항목을 유지한다. 전체 실제 사용자 흐름 완료는 이 acceptance가 끝난 뒤 판단한다. Git add/commit/push는 계속 사용자 담당이다.
