### 발견·수정한 독립 결함

`infra/systemd/moneyworry-conversation-maintenance.service.in`이 `NoNewPrivileges=true`를 사용하고 `RestrictSUIDSGID`를 생략해, autodeploy 하나만 권한 완화를 허용하는 기존 infra 계약을 깨뜨렸다. `NoNewPrivileges=yes`와 `RestrictSUIDSGID=yes`로 맞췄다. worker는 다른 계정 가장이나 setgid 생성이 필요 없으므로 동작 범위를 넓히지 않는 보안 강화다. 수정 뒤 contract/infra/GCP Linux job이 전부 통과했다.

### 실패 기록과 PostgreSQL semantic 차단

1. 첫 DB runner는 Node checksum 선택용 보조 `grep` 인용이 PowerShell 경계를 지나 깨져 테스트 전 종료했다. checksum 전체 파일 검사로 바꿨다.
2. 다음 runner는 migration 적용까지 성공했으나 Debian Python image에 `psql`이 없어 live drift가 `spawnSync psql ENOENT`였다. PG16 client image에서 snapshot/live drift/replay를 완료했다.
3. RAG root runner는 verifier가 root라 read-only 권한 unit 1개가 실패했다. 비-root로 재실행했다. 첫 비-root tmpfs는 모델 파일 10개 중 9개 뒤 공간 부족이었고, 라벨 전용 volume에서 최종 완료했다.
4. PG semantic/canonical 스크립트를 Python Linux runner에서 실행하려면 runner에 Docker daemon socket을 넘겨야 했다. 자동 승인 검토는 이 방식이 관련 없는 container/volume/network까지 제어할 수 있는 root 상당 권한이라고 거부했다. WSL enumeration도 `E_ACCESSDENIED`, host Git Bash에는 Python3가 없다. 우회하지 않았으며 아래를 **신뢰된 Linux host에서 직접** 재개한다.

```bash
cd db
export PATH_B_TEST_POSTGRES_IMAGE='postgres:16-alpine@sha256:cf78e76683b9ca8c5733cbbdce6c9262b45b6767934dd0a95e671f9a0fc20685'
npm run test:path-b-pg16-semantic
npm run test:path-b-pg16-canonical
```

따라서 로컬 Linux 상당 검사는 강한 PASS 근거지만, GitHub Actions 전체 green 또는 추가 PG semantic PASS로 부르지 않는다.

## 5. 정책 결정표

### P1. 공개 회사 검색의 total/filter count

- **현재 구현/노출:** search가 exact `total`/`total_pages`, filters가 지역·업종별 exact `count`를 익명에 반환한다.
- **보안·제품 영향:** 검색 UX에는 유용하지만 반복 조합으로 모집단 추정과 열거가 쉽다.
- **추천 기본안/대안:** `has_more`와 상한 표시(`1000+`) 및 필터 구간값. 대안은 exact 유지+강한 rate limit, 또는 count 제거.
- **결정권자:** Product Owner + API/Security + 데이터 책임자.
- **결정 뒤 변경:** `companyService.ts`, DTO/UI, real/mock count query, API tests/docs.
- **미룰 때 영향:** 코드 PR 검토는 가능하지만 공개 출시·단계13 완료 불가.

### P2. 페이지 상한, deep enumeration, rate limit

- **현재 구현/노출:** limit 1~20, page 1~100,000, offset 검색, 검색 rate limit 없음. `sec-fetch-site`는 rate limit이 아니다.
- **보안·제품 영향:** 최대 2,000,000 위치 요청, DB 부하·scraping 가능성이 있다.
- **추천 기본안/대안:** 공개 window 1,000건(20×50), 이후 cursor/정확명 검색, IP+세션 30회/분 burst와 429. 대안은 인증 후 확장 또는 더 낮은 window.
- **결정권자:** Product Owner + API/Security + SRE.
- **결정 뒤 변경:** validation/DTO/UI, rate limiter/storage, route tests, 운영 관측/runbook.
- **미룰 때 영향:** 대량 조회/침투 인수와 단계13 차단.

### P3. 공개 risk band와 model metadata

- **현재 구현/노출:** raw score/rank/SHAP는 제외하지만 wage/safety `level`, availability, confidence, evidence, 기간과 source `document_id`를 공개한다. latter에는 model version/batch id 또는 safety model name/version이 들어갈 수 있다.
- **보안·제품 영향:** band는 설명 가능성을 높이지만 낙인 위험이 있고 내부 식별자는 불필요한 계약 고정을 만든다.
- **추천 기본안/대안:** 검토된 의미 band·availability/confidence·as-of·stable public model-card ID만 유지하고 내부 batch/pipeline 이름 제거. 대안은 metadata 전체 제거 또는 투명성 문서 링크.
- **결정권자:** Product Owner + ML + Legal/Security.
- **결정 뒤 변경:** risk domain/provider, public DTO/cards/chat context, tests/data-contract.
- **미룰 때 영향:** 필드 allowlist 회귀는 가능하지만 공개 의미 승인·단계13 완료 불가.

### P4. 익명 상담 quota

- **현재 구현/노출:** 비로그인도 same-origin 검사 후 실제 provider를 호출하며 server quota가 없다. DB에는 저장하지 않고 탭 sessionStorage에 한 상담을 둔다.
- **보안·제품 영향:** 비용 폭증·자동화 남용·IP 우회 위험이 있다.
- **추천 기본안/대안:** IP+브라우저 10회/시간·30회/일과 전체 provider 예산 circuit breaker. 대안은 로그인 전 3회, CAPTCHA 결합, 익명 비활성.
- **결정권자:** Product Owner + Finance/SRE + Security.
- **결정 뒤 변경:** `/api/chat`, quota store, UI/metrics/alerts, 이용 안내.
- **미룰 때 영향:** 공개 provider 배포 승인 불가.

### P5. feedback 연결 및 보존

- **현재 구현/노출:** chat feedback은 same-origin/64 KiB와 UUID·선택·metric을 검증해 `.runtime/comparison-feedback.jsonl`에 append한다. 인증, 발급 UUID 확인, user/conversation FK, TTL/rotation이 없다. DB `feedback`은 별도 커뮤니티 테이블이다.
- **보안·제품 영향:** 평가 연결성이 약하고 삭제·백업 범위가 불명확하다.
- **추천 기본안/대안:** 서버 발급 comparison ledger 확인, nullable/pseudonymous user, 필요할 때만 conversation link, 원문 없이 90일 TTL. 대안은 익명 aggregate 30일 또는 로그인 평가만.
- **결정권자:** Product/ML 평가 + Privacy/Security.
- **결정 뒤 변경:** feedback repository/schema 또는 로그 파이프라인, route/auth, purge/backup, notice/tests.
- **미룰 때 영향:** 실험용 한계로만 유지하며 공개 평가 인수 차단.

### P6. 상담 원문 30일과 기타 기록 90일

- **현재 구현/노출:** thread 활동 때 sliding 30일이며 messages/turns/sources/summaries/requests/company events가 cascade 삭제된다. 90일은 미구현 draft event 설계다.
- **보안·제품 영향:** 파생 요약만 더 오래 남기면 원문 삭제 기대와 충돌하고, 장기 개인화는 별도 목적이 필요하다.
- **추천 기본안/대안:** 상담 원문·요약·sources·ledger를 함께 30일, 관심은 favorites가 정본; 90일 cross-feature event는 별도 목적·고지·삭제권 승인 뒤 도입. 대안은 opt-in만 90일.
- **결정권자:** Product Owner + Privacy/Legal + DB.
- **결정 뒤 변경:** privacy UI/docs, worker, 필요 시 migration/API.
- **미룰 때 영향:** 30일 기술 증거는 재사용 가능하나 개인정보 정책·단계13 미완료.

### P7. backup 삭제 반영 시점

- **현재 구현/노출:** live expiry/cascade는 있으나 backup catalog, TTL, restore 후 재삭제 계약은 없고 기술적으로 미검증이다.
- **보안·제품 영향:** 삭제 고지와 복원 가능한 데이터가 달라질 수 있다.
- **추천 기본안/대안:** live 즉시 삭제, backup 최대 30일, restore 시 tombstone/expiry cutoff 재적용 후 개방. 대안은 더 짧은 TTL, 키 폐기, legal hold 예외.
- **결정권자:** Privacy/Legal + DB/SRE + Security.
- **결정 뒤 변경:** backup/restore runbook, retention config, deletion journal 필요성, restore rehearsal.
- **미룰 때 영향:** 개인정보·복구 인수와 운영 배포 차단.

### P8. 탈퇴 삭제 범위

- **현재 구현/노출:** 탈퇴 API/UI가 없다. 물리 user delete의 conversation FK cascade는 격리 PG16에서 확인했지만 chat JSONL feedback은 user FK가 없다.
- **보안·제품 영향:** 일부 식별 데이터 잔존 및 late write 위험이 있다.
- **추천 기본안/대안:** 원문·요약·sources·company events·request ledger·식별 가능한 chat feedback 삭제, 최소 비식별 운영 감사만 별도 TTL. UGC 법적 예외는 작성자 비식별화.
- **결정권자:** Product Owner + Privacy/Legal + DB/API.
- **결정 뒤 변경:** deletion API/UI, transaction/cascade, feedback storage, worker/backup docs, late-write tests.

### P9. 외부 LLM 전송·고지·공급자 보존

### P12. `chat_memory_consents`

- **현재 구현/노출:** 초안뿐이고 inspector 동의는 request boolean이다. provider/expiry/revoked_at을 durable하게 기록하지 않는다.
- **보안·제품 영향:** 지속 동의가 필요하면 감사·철회가 불가능하고, 매 요청 동의면 새 테이블은 과잉 저장이다.
- **추천 기본안/대안:** P9/P10에서 동의를 기간 재사용하기로 결정할 때만 목적 전용 table 도입. 대안은 짧은 conversation/provider-scoped consent; 매 요청이면 미도입.

- **결정 뒤 변경:** migration/role, consent API/UI, revoke/expiry worker/tests.

### P13. crash-pending 요청 UX

- **현재 구현/노출:** 생성 전 pending claim, crash 뒤 같은 request는 retryable 409 `CHAT_REQUEST_IN_PROGRESS`; completed replay만 durable하다. 생성 후 저장 실패 cache는 process-local 5분이고 request lease/reclaim이 없다.
- **보안·제품 영향:** orphan pending 영구 대기와 새 request id의 중복 provider 호출 가능성이 있다.
- **추천 기본안/대안:** 2분 processing lease 후 `failed_retryable`, 같은 request id 재claim; UI는 처리 중 재시도 시각과 만료 후 저장 확인/재생성 안내. 대안은 새 request만 허용하거나 durable outbox.
- **결정권자:** Product Owner + Backend/DB + SRE.
- **결정 뒤 변경:** request migration/status/lease, repository/route/worker, ChatPanel, crash/concurrency/restart tests.
- **미룰 때 영향:** 정상 replay 증거는 재사용 가능하나 crash 인수 없이 단계13 완료 불가.

2. 최신 `origin/main` 통합 후 target SHA, GitHub CI, immutability, snapshot 0 diff를 확인한다.
3. backup 형식·SHA-256·복원 가능성·retention을 확인하고 운영 DB read-only drift를 실행한다. `partial/schema_ahead/diverged`면 중단한다.
4. 승인 migration만 번호 순서로 적용한다. 현재 기준 0019는 worker보다 먼저 필요하다. 기적용 SQL/hash/ledger를 수정하거나 DB를 초기화하지 않는다.
5. live drift 후 auth/conversation role grant를 migration 이후 실행한다. 비밀번호는 env/`\getenv`로만 전달한다.
6. 앱 build/deploy 후 readiness·로그인·owner isolation·저장/replay를 확인한다. guarded exit 3은 자동 재시도하지 않는다.
7. 같은 SHA에서 worker bundle을 별도 build하고 `systemd-analyze verify` 후 oneshot 1회, 개수 로그만 확인한다.
8. timer enable/start 후 backlog·lease·stale pending·expiry와 승인된 backup/탈퇴/철회 smoke를 본다.
9. 오류 시 worker/timer를 먼저 중지하고 앱 호환성을 확인한다. ledger/기적용 migration을 되돌려 쓰지 않는다.
