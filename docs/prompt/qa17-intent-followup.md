# QA #17-3: PR #80 이후 상담 처리 방향을 바꾼 이유

## 팀원에게 먼저 전달할 요약

PR #80은 부동산·투자·프로그래밍 등의 범위 밖 표현을 검색 분류에 추가하고, 그 경로에서 회사 요약이 나오는 문제를 줄인 수정입니다. 다만 후속 검사에서 단어 조합에 따라 정상 노동 질문을 막거나, 엉뚱한 질문을 회사 상담으로 판단하는 한계가 남았습니다.

이번 후속 변경은 **모든 엉뚱한 질문을 단어 목록으로 완벽히 잡겠다는 목표를 내려놓고, 질문의 요청 목적을 먼저 분류한 뒤 불확실하거나 실패하면 확인 질문으로 멈추는 방식**입니다. 회사 지표 질문은 법령 검색에 실패해도 회사 자료로 설명하고, 근거 없는 법률 답변은 만들지 않습니다.

## 1. PR #80에서 한 일과 남은 한계

- [PR #80](https://github.com/SeD-ShallweData/2nd_Side2026_Project/pull/80)은 main에 병합됐습니다.
- 부동산·세금·투자·프로그래밍을 범위 밖 주제로 추가했습니다.
- 해당 분류에서는 회사 요약 대신 범위 설명과 공식 창구를 반환하도록 했습니다.
- 목록에 없는 질문도 회사 노동 질문으로 보이지 않으면 회사 요약을 지우도록 보완했습니다.
- 그러나 ‘회사’와 ‘안전’이 함께 있으면 게임 설치 질문도 회사 노동 질문으로 통과했습니다. 반대로 코딩과 야근수당·구어체 잔업 표현이 섞인 정상 질문이 범위 밖으로 분류될 수 있었습니다.

이는 단어 목록을 조금 더 늘리면 끝나는 문제가 아닙니다. ‘월급으로 주식 추천’에는 노동 단어가 있지만 요청 목적은 투자이고, ‘부동산 시세 분석 일을 하는데 월급이 밀림’은 부동산 표현이 있어도 노동 상담입니다.

## 2. 프롬프트만으로 해결할 수 없었던 이유

기존 경로는 검색 실패 시 답변 생성 모델을 호출하지 않고 미리 만든 정책 답변을 반환했습니다. 회사가 선택돼 있으면 그 답변이 회사 요약일 수 있었습니다. 이 경로에서는 답변 프롬프트의 규칙이 실행될 기회가 없습니다.

모델을 호출하는 경우에도 모든 표현·오타·생략·복합 의도를 항상 정확하게 이해한다고 보장할 수 없습니다. 따라서 프롬프트 개선과 함께 **의도 판단, 근거 유무, 회사 자료 사용, 실패 시 대체 답변**을 분리해야 합니다.

## 3. 이번 후속 변경

현재 시연 사이트가 사용하는 `dual_api` 상담 경로를 대상으로 합니다. 기본 Upstage 단일 답변과 Upstage/SKT 비교 모드가 이 경로를 공유합니다.

1. 기존 긴급 정책을 먼저 적용합니다. 긴급 응답은 새 분류 모델을 기다리지 않습니다.
2. 일반 질문은 작은 분류 호출로 `노동 상담 / 회사 지표 / 무관한 질문 / 불확실` 중 하나로 구분합니다. 회사 선택 자체가 회사 질문이라는 근거는 아닙니다.
3. 무관한 질문에는 상담 범위를 알리고, 분야를 확인한 경우 코드에 등록된 공식 창구만 안내합니다. 모델이 URL을 임의로 만들지 않습니다.
4. 불확실한 질문, 분류 API 실패, 잘못된 JSON은 확인 질문으로 처리합니다. 회사 요약을 대신 내보내지 않습니다.
5. 노동 질문은 관련 검색 근거가 있으면 답변을 생성하고, 없거나 검색 서비스가 실패하면 상황을 구체화하는 질문을 반환합니다. 검색 주제 단어만으로 ‘노동 질문이 아니다’라고 단정하지 않습니다.
6. 회사 지표 질문은 사업장을 선택하도록 요청하거나, 선택 회사 자료로 의미와 한계를 설명합니다. 법령 검색 실패가 회사 정보 설명을 막지 않습니다.
7. 답변 생성 뒤 가드레일에 걸리거나 모델 API가 실패해도 미리 만든 회사 요약을 대체 답변으로 사용하지 않습니다.

Python 검색에서도 비노동 주제 단어 때문에 통과 가능한 노동 근거나 공식 가이드를 버리지 않도록 바꿨습니다. 기존 노동 인접 주제의 검색 정책과 새 비노동 주제 힌트는 구분합니다.

실제 실행 프롬프트는 `product/prompts/chat/system.md`입니다. `docs/prompt/CONTENTS.md`는 설명 문서이며, 이번 변경은 두 파일 모두에 반영했습니다.

## 4. 사례별 기대 동작

| 질문 | 처리 목표 |
| --- | --- |
| 회사 컴퓨터에 게임을 안전하게 설치하려면? | 회사·안전 단어에 끌려가지 않고 범위 안내 |
| 월급으로 주식 투자할 종목 추천 | 임금체불 안내가 아닌 범위 안내 |
| 코딩을 밤 10시까지 시키고 돈은 더 안 준다 | 노동 상담으로 검색. 근거 부족 시 근무 조건 확인 |
| 코딩 부서로 입사하는데 회사 지표가 나에게 적용되는가? | 회사 자료로 설명. 업종 통계를 개인 위험으로 환산하지 않고 필요하면 현장 업무 포함 여부 확인 |
| 긍정 지표가 없으면 나쁜 회사인가? | 미확인과 부정 판정을 구분하고 확인된 자료의 범위에서 설명 |
| 지시대상이 없는 “그건 어떡해?” | 추측 대신 확인 질문 |

이 표는 설계 목표입니다. 새 분류 모델의 실제 정확도나 수정 후 배포 사이트에서 모두 통과했다는 결과표가 아닙니다.

## 5. 검증 결과를 구분해서 봐야 합니다

- 수정 전 시연 사이트에서 20개 질문 × 회사 선택 전/후 = 40회 실제 API 검사를 했습니다. HTTP 200은 답변 품질 통과를 뜻하지 않으며, 무관한 질문 8개의 회사 선택 상태에서 모두 회사 요약이 나왔습니다.
- 그 사이트는 명시적 범위 밖 분기에서도 PR #80의 main과 다른 응답을 반환했습니다. 배포 불일치가 의심되지만 실제 서버 commit은 확인하지 못했습니다. main 병합과 서비스 배포는 별개입니다.
- 이번 후속 변경의 단위·경로 테스트는 분류 결과에 따른 처리, 분류 실패, 검색 실패, 긴급 우선, 공급자 비교, 가드레일/API 오류 시 회사 요약 제거를 검증합니다. 분류 모델은 모의 응답을 사용하므로 의미 분류 정확도를 측정한 것이 아닙니다.
- 로컬 `npm run check`: 웹 테스트 711개 통과, 실제 모델 평가 32개는 명시적으로 건너뜀, 타입 검사·lint·빌드 통과(기존 unused error 경고 1개). Python 검색 테스트 16개 통과.
- 실제 모델 분류 평가용 합성 질문 16개를 회사 선택 전/후로 실행하는 도구도 포함했습니다. 이번 작업 환경에는 해당 모델 자격증명이 없어 실제 평가는 아직 실행하지 않았습니다.

모델 키가 정상 설정된 product 환경에서 아래 평가를 실행할 수 있습니다. 실제 모델 32회 호출 비용이 발생합니다. 인증정보를 결과 문서에 넣지 않습니다.

```powershell
$env:RUN_CHAT_INTENT_LIVE = "1"
npx vitest run src/services/chatIntentLive.test.ts
Remove-Item Env:RUN_CHAT_INTENT_LIVE
```

## 6. 남는 한계와 비용

- 분류 모델도 오분류할 수 있습니다. 올바른 형식의 오답까지 JSON 검사가 찾아내지는 못합니다.
- 모호한 질문은 바로 답하지 않고 되물으므로 편의성이 일부 줄어들 수 있습니다.
- 일반 요청마다 분류 모델 호출이 한 번 추가됩니다(최대 출력 100토큰, 타임아웃 8초). 후속 질문 재작성과 최종 답변 생성은 별도입니다. ‘단일 모델 답변’이 전체 API 호출 1회를 뜻하지 않습니다.
- 기존 결과의 모델 사용량·지연 지표는 최종 답변 모델 기준입니다. 분류와 재작성 비용까지 포함한 전체 요청 비용/시간으로 해석하면 안 됩니다.
- 모델이 잘못 company로 판단하면 무관한 질문에도 회사 자료를 이용한 생성 경로에 들어갈 가능성이 남습니다. 원문 우선·불확실하면 되묻기 지침과 출력 가드레일을 함께 사용하지만 완전한 차단을 보장하지 않습니다.
- 노동 질문으로 분류된 경우 선택 회사 자료를 자동 주입하지 않습니다. 회사 지표 질문과 일반 노동 상담을 분리하는 선택이며, 실제 질문에서 문맥 손실이 없는지도 검증해야 합니다.
- `openai_responses`의 도구 실행 제어는 이번 변경 대상이 아닙니다. 공유 답변 프롬프트의 문구는 영향을 받을 수 있으므로 해당 모드를 사용할 팀은 별도 회귀 확인이 필요합니다.
- 법률 내용의 정확성, 반복 생성, 장기 대화, 모든 긴급 표현까지 이번 테스트만으로 검증한 것은 아닙니다.

## 7. 팀 검토 요청

창의와 상담 담당자는 의도 분류 후 검색·회사 자료 사용 흐름과 추가 호출 비용을, 성현은 가드레일 교체·불확실 경로를 확인하면 됩니다. 배포 담당자는 웹/RAG 실행 버전 일치부터 확인해야 합니다.

권장 순서는 **코드/CI 검토 → 실제 분류 평가 → 스테이징에서 동일 질문 전후 비교 → 병합·배포 → 실제 화면 회귀**입니다. 새 분류의 실측 결과가 아직 없으므로 후속 PR은 초안으로 제출합니다. 팀원에게 별도 메시지를 보내거나 서비스를 배포하지는 않았습니다.
