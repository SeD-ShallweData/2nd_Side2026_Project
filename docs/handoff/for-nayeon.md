## N1. 댓글 조회 권한을 공용 스크립트에 반영해 주세요

**구분: 통보 (민규가 이미 반영함)**

게시글 목록·상세에 표시하는 댓글 수를 만들 방법이 없었다. `wg_community`에 부여된 대상은
게시글·신고·사업장·`v_posts`·피드백뿐이고 댓글 테이블이 빠져 있었다.

민규가 `db/scripts/create-community-role.sh`에 아래 한 줄을 추가했다.

- 댓글 테이블에 **조회 권한만** 부여
- 댓글 작성·수정·삭제 API가 아직 없으므로 쓰기 권한은 부여하지 않음
- 댓글 기능을 만드는 시점에 쓰기 권한을 명시적으로 추가하라고 주석에 남김

"새 테이블은 매번 명시적으로 GRANT 한다"는 나연의 설계 원칙을 따랐다.

**나연이 할 일**: 현재 민규 브랜치에만 있다. 다른 팀원 환경과 운영 서버에도 적용되려면
본선 코드에 반영이 필요하다. 이미 롤이 만들어진 환경에서는 권한 부여를 한 번 더 실행해야 한다.

## N2. 롤을 먼저 만들고 마이그레이션을 돌려야 합니다

**구분: 통보 (실제로 겪은 문제)**

`0009` 마이그레이션 끝의 권한 부여는 "해당 롤이 이미 있을 때만" 실행되는 조건부 블록이다.
롤이 없으면 **오류 없이 조용히 건너뛴다.**

그런데 새 DB를 만들 때 자연스러운 순서는 스키마 적용이 먼저고 롤 생성이 나중이다.
그 순서로 하면 `wg_community`의 `v_posts`·피드백 권한이 빠진 채로 남는다.

2026-09-04 민규 로컬에서 실제로 발생했다. 조용히 실패하기 때문에 나중에
**"비익명 글인데 작성자 이름이 안 나온다"는 증상으로만 드러난다.**

해당 블록만 다시 실행해서 해결했고, 재실행해도 안전한 것을 확인했다.

**나연이 할 일**: `db/README.md`나 스크립트에 올바른 순서를 명시해 주면 좋겠다.
"롤 생성 → 마이그레이션" 순서이거나, 마이그레이션을 이미 돌렸다면 권한 블록 재실행이 필요하다.

## N3. 인증·커뮤니티 롤이 분리돼서, 요청 하나에 커넥션 두 개를 씁니다

**구분: 확인 요청**

두 롤의 권한이 겹치지 않는다.

| 롤 | 접근 가능 | 접근 불가 |
| --- | --- | --- |
| `wg_auth` | 회원, 세션 | 게시글, 신고, 사업장 |
| `wg_community` | 게시글, 신고, 사업장, `v_posts`, 댓글(조회), 피드백 | **회원, 세션** |

민규 로컬에서 실제로 경계를 확인했다. 인증 롤로 게시글을 읽으면 거부되고,
커뮤니티 롤로 회원을 읽으면 거부된다. 설계대로 동작한다.

그래서 게시글 작성 한 건이 이렇게 흐른다.

1. 인증 커넥션으로 세션을 확인해 작성자와 권한 등급을 알아낸다
2. 커뮤니티 커넥션으로 게시글을 저장한다

**결과**: 두 동작을 한 트랜잭션으로 묶을 수 없다. 1번이 성공하고 2번이 실패하면
되돌릴 것 없이 그냥 "작성 실패"로 끝난다. 최소권한 원칙상 올바른 구조로 보이지만,
이 대가를 감수하는 설계가 맞는지 확인하고 싶다.

**질문**: 의도한 구조가 맞나? 아니라면 어느 쪽으로 조정할 생각인가?

## N4. `wg_bot`을 로컬에서 만들 방법이 있나요

**구분: 질문**

`create-bot-role.sh`를 단독 실행하면 Path B 세션 identity 가드에 막힌다.
승인된 DB인지 대조하는 값 4개를 요구하는데, 새 로컬 DB에서는 확보할 수 없다.

이번 인증·커뮤니티 작업에는 필요 없는 롤이라 넘어갔다. 다만 나중에 AI 상담까지
로컬에서 붙이려면 필요해진다.

**질문**: `bootstrap:path-b` 절차를 밟는 것 말고 로컬 개발용 경로가 있나?
없다면 로컬에서는 AI 상담 연동을 검증하지 않는 것으로 정리해도 되나?

## N5. 비밀번호 저장 형식을 확정했습니다

**구분: 공유 (지금 조치는 불필요, 계정을 만들 일이 생기면 필요)**

회원 테이블의 비밀번호 항목에 무엇을 넣을지 정의가 없었다. 2026-09-04에 확정했다.

```
scrypt$<N>$<r>$<p>$<salt-base64>$<hash-base64>
```

- 알고리즘은 **scrypt**. Node 내장이라 의존성이 늘지 않고, 메모리를 많이 쓰도록
  설계돼 있어 전용 장비를 동원한 대량 대조에 강하다.
- 현재 매개변수는 `N=16384`, `r=8`, `p=1`, 키 32바이트, salt 16바이트.
- **매개변수를 저장값에 함께 적는다.** 나중에 세기를 올려도 예전 비밀번호를
  그대로 검증할 수 있어야 하기 때문이다.
- 기준 구현은 `product/src/server/auth/passwordHash.ts` 하나뿐이다.
  다른 곳에서 같은 형식을 다시 만들면 어긋날 수 있으니 이 파일을 기준으로 삼는다.

**나연이 알아야 할 때**: 운영용 계정이나 시드 회원을 직접 만들 일이 생기면
이 형식으로 넣어야 로그인이 된다. 형식이 다르면 계정은 멀쩡한데 로그인만 실패한다.
일반 사용자 계정은 민규가 만드는 회원가입 API로 생기므로 보통은 신경 쓸 일이 없다(N9).

## N6. `seed_local.sql`을 본선 코드에 병합해 주세요

**구분: 요청**

감독관 화면용 시드가 나연 브랜치(`task/user-db-migration`)에만 있다.
민규는 본인 브랜치로 커밋을 그대로 옮겨(작성자 나연 유지) 로컬 검증에 썼고,
사업장 7곳·감독관 큐 5건이 정상 적재되는 것을 확인했다.

본선 코드에 없으면 다른 팀원이 같은 검증을 못 한다. 병합해 주면 좋겠다.

## N7. Windows에서는 롤 스크립트를 그대로 실행할 수 없습니다

**구분: 참고 (조치 요청 아님)**

민규 개발 환경이 Windows라 세 군데서 막혔다.

1. 호스트에 `psql`이 없다 — DB는 컨테이너로만 접근 가능
2. Windows 체크아웃이라 줄바꿈 문자가 붙어 스크립트 첫 줄에서 실패한다
3. 파일 권한 0600 검사를 통과할 수 없다 — Git Bash가 NTFS에서 권한 모드를 표현하지 못한다

**스크립트는 고치지 않았다.** 권한 검사는 공용 서버를 위한 올바른 방어라 임의로 완화하면 안 된다.
대신 스크립트를 컨테이너 안으로 복사해 원본 그대로 실행하는 방식으로 우회했다.

공유하는 이유는, 다른 Windows 팀원이 같은 벽에 부딪혔을 때 스크립트를 고치려 들지 않게
하기 위해서다. 필요하면 우회 절차를 문서로 정리하겠다.

## N8. 제보용 테이블과 파일 저장소

**구분: 요청 (별도 문서, 아직 착수 전)**

현장 제보 API는 이번 실제 DB 연결 범위에서 **제외**했다. DB와 프론트 어느 쪽에도
전달되지 않은 상태라 아직 연결할 수 없다.

요청 내용은 [`DB_HANDOFF_NAYEON.md`](../../product/src/app/api/worksite-tips/DB_HANDOFF_NAYEON.md)에 정리돼 있다.
그 문서에서 나연·윤빈 결정을 기다리는 항목은 세 가지다.

- `wg_community`를 확장할지, 민감 제보용 별도 롤을 만들지
- 사진 원본을 어디에 둘지
- 본문·사진이 모두 없는 제보를 DB에서 막을지 애플리케이션에서만 막을지

여기에 민규가 추가로 확인한 정책 문제가 하나 있다. 업로드된 사진의 촬영 위치·시각·기기 정보가
감독관에게 그대로 전달된다. 증거 원본 보존과 제보자 개인정보 보호가 충돌하는 지점이라
실제 저장소를 붙이기 전에 정책을 정해야 한다.

## N9. 회원가입 API는 민규가 맡습니다

**구분: 공유**

실제 DB에는 회원이 0건이고 회원가입 기능도 없어서, 그대로 전환하면 아무도 로그인할 수 없다.
나연에게 시드 회원을 요청하는 대신 **민규가 회원가입 API를 만들어 해결하기로 했다.**

만들면서 지키는 것

- 가입 시 직업 구분을 받는다 (회원 테이블이 필수로 요구함)
- 가입은 일반 사용자로 고정한다. 감독관·관리자는 가입으로 만들 수 없다
- 사업장 연결은 사업주·기업 담당자로 가입할 때만 허용한다 (DB 제약과 동일)

2026-09-04 구현을 마쳤다. `POST /api/auth/signup` 으로 계정을 만들 수 있으므로,
**나연이 시드 회원을 따로 만들어 줄 필요가 없다.**

## N10. wg_auth 에 firms 조회 권한이 없는 것은 그대로 두었습니다

**구분: 공유 (조치 요청 아님)**

가입할 때 사업장을 연결할 수 있는데, `wg_auth` 롤에는 `firms` 조회 권한이 없어서
앱이 사업장 존재 여부를 미리 확인할 수 없다.

**권한을 늘려 달라고 하지 않았다.** 대신 외래키 위반(23503)을 받아 "선택한 사업장을
찾을 수 없습니다"로 바꿔 보여준다. 결과는 같고, 인증 계정이 볼 수 있는 범위는
회원·세션 두 테이블로 유지된다 — 최소권한 원칙을 깨지 않는 편을 택했다.

혹시 다른 이유로 `firms` 조회 권한을 주는 게 낫다고 보면 알려주면 좋겠다.


## N11. 숨겨진 글의 작성자 이름을 가져올 수 없습니다

**구분: 확인 요청 (지금은 우회해 두었음)**

`wg_community` 는 `users` 에 접근할 수 없어서, 작성자 이름을 `v_posts` 뷰에서 가져온다.
익명 처리가 뷰 안에 들어 있어 앱에서 다시 처리하지 않아도 되는 좋은 구조다.

그런데 `v_posts` 는 `status = 'published'` 인 글만 담는다. 그래서 **신고 승인으로
숨겨진 글은 작성자 이름을 알 수 없다.**

| 상황 | 작성자 이름 |
| --- | --- |
| 공개된 실명 글 | 정상 |
| 익명 글 | 원래 나오지 않음 (정상) |
| **숨겨진 실명 글** | **알 수 없음** |
| 삭제된 글 | 조회 자체가 404 라 무관 |

지금은 이름을 모를 때 빈 문자열이 아니라 `null` 로 내보내도록 처리했다. 빈 문자열은
화면에 그대로 찍혀 "이름이 없는 사람"처럼 보이기 때문이다.

영향 범위는 좁다. 숨겨진 글을 볼 수 있는 사람은 관리자와 작성자 본인뿐이고,
신고 관리 화면은 작성자 이름을 쓰지 않는다.

**질문**: 이대로 두어도 되나? 아니면 `v_posts` 의 상태 필터를 조정하거나
관리자용 뷰를 따로 두는 게 나을까? 뷰는 나연 영역이라 임의로 건드리지 않았다.

## N12. 재신고 허용 범위가 DB 설계와 API 규칙이 다릅니다

**구분: 확인 요청**

`reports` 의 유니크 인덱스에 주석이 이렇게 적혀 있다.

> 대기중(pending) 신고만 중복 방지 — 기각된 뒤 재신고는 허용

그런데 **현재 API 규칙은 상태와 무관하게 재신고를 막는다.** 한 번 신고했으면
그 결과가 기각이든 승인이든 다시 신고할 수 없다.

| | 재신고 허용 여부 |
| --- | --- |
| 나연의 DB 설계 | 기각된 뒤에는 **허용** |
| 현재 API 규칙 | 언제나 **차단** |

앱이 더 엄격하므로 충돌해서 오류가 나지는 않는다. 이번 작업에서는 **동작을 바꾸지 않는
것이 원칙**이라 현재 규칙을 그대로 두었다.

어느 쪽이 맞는지 판단이 필요하다. 기각 후 재신고를 허용하면, 글이 수정되어 새로 문제가
생긴 경우를 다룰 수 있다. 막으면 같은 신고가 반복되는 것을 줄인다.
