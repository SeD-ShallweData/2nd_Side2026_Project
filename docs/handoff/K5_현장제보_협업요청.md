## 2. 현재 확정·구현된 정책

| 항목 | 현재 정책 |
| --- | --- |
| 제보 카테고리 | `wage`(임금), `safety`(산재) 중 하나를 필수 선택 |
| 처리 상태 | `received`(접수완료), `in_progress`(처리중), `completed`(처리완료) |
| 최초 상태 | 모든 신규 제보는 `received` |
| 일반 사용자 | 접수 직후 영수증만 확인. 본인 제보 이력 조회·수정·삭제·철회 기능은 현재 범위에서 제외 |
| 감독관 | 목록·상세·사진 조회만 가능. 상태 변경 기능은 현재 범위에서 제외 |
| 관리자 | 현장 제보 조회 권한 없음 |
| 목록 정렬 | `received` → `in_progress` → `completed`, 같은 상태에서는 최신 접수순 |
| 신원 보호 | 이메일·내부 사용자 ID·원본 파일명·원본 사진과 EXIF를 일반 사용자와 감독관 모두에게 비노출 |
| 사진 제공 | 감독관에게는 EXIF·XMP·IPTC가 제거된 사본만 제공 |
| 저장 구조 | 본문과 사진 메타데이터는 PostgreSQL, 사진은 VM 비공개 영구 저장소 |

처리 상태는 세 종류를 저장할 수 있지만, 이번 범위에는 상태를 바꾸는 주체와 API가 없습니다.
따라서 새로 접수되는 제보는 당분간 모두 `received`로 유지됩니다. `in_progress`와 `completed`는
향후 상태 변경 정책이 정해졌을 때 사용합니다.

## 3. K5 필수 고지 문구

접수 화면에는 아래 문구를 그대로 표시해야 합니다.

> 본 제보함은 신고자의 익명성과 프라이버시를 철저히 보호하며, 입력된 정보는 공공 노동 정보 서비스의 확인 및 점검 참고용으로만 안전하게 활용됩니다.

기존 J3 과업에 있던 “사진의 위치 정보는 제거되며 비공개로 접수됩니다” 문구와 위 K5 문구를
한 화면에 어떻게 배치할지는 민서의 최종 검수를 요청합니다. K5 문구는 필수이며 생략하거나
뜻을 줄여 쓰지 않습니다.

## 4. 나연에게 요청할 사항

### 요청 1 — `0013` 마이그레이션 검토

다음 변경이 DB 설계 의도와 맞는지 확인 부탁드립니다.

- `worksite_tips.category`를 임금·산재 두 값으로 제한
- 기존 `worksite_tip` 값은 `safety`로 변환
- 처리 상태 컬럼을 추가하고 기본값을 `received`로 지정
- 상태 값을 세 종류로 제한
- 상태 우선순위와 최신순 조회를 위한 인덱스 추가

특히 기존 데이터를 모두 산재로 변환하는 정책이 적절한지 확인 부탁드립니다. 기존 값만으로는
임금·산재를 구분할 수 없으므로, 자동 변환 단계에서는 기존 현장 위험 제보를 산재로 분류했습니다.

### 요청 2 — N7 조회 뷰 불필요 판단 확인

현재 감독관 목록은 `worksite_tips` 원본 테이블을 `wg_tip` 계정으로 직접 조회하고,
API 조회문에서 상태 우선순위와 최신순 정렬을 수행합니다. K5에는 복잡한 집계나 여러 테이블의
결합 조건이 없어 별도 조회 뷰를 만들지 않았습니다.

N7은 “현재 요구사항에서는 별도 뷰 불필요”로 종료해도 되는지 확인 부탁드립니다. 추후 지역·기간·
사업장별 복합 필터나 집계가 추가되면 그때 뷰 도입을 다시 검토하면 됩니다.

### 요청 3 — GCP 적용 전 검증과 적용 순서 확인

- 운영 DB를 먼저 백업
- 운영 migration 원장을 확인하고 미적용 migration을 번호순으로 적용
- `0012`가 미적용이면 `0012` 다음에 `0013` 적용
- 적용 후 migration drift 검사 수행
- 기존 행의 카테고리 변환, 상태 기본값·제약·인덱스 확인
- `wg_tip`의 현장 제보 테이블 `SELECT·INSERT` 권한 확인

이번 API에는 상태 변경 기능이 없으므로 `wg_tip`에 `UPDATE` 권한을 추가할 필요는 없습니다.
운영 DB 적용에는 DB 소유자 권한이 필요할 수 있으므로, 나연이 검토한 뒤 윤빈과 실제 적용 일정을
맞춰 주세요.

### 나연 확인 완료 기준

- `0013` 내용과 기존 데이터 변환 정책에 이상이 없다는 회신
- N7을 별도 뷰 없이 종료해도 된다는 회신
- GCP 적용 담당자와 적용 순서 확정

## 5. 지유에게 요청할 사항

### 요청 1 — 일반 사용자 접수 화면 연결

접수 화면에서 다음을 처리해 주세요.

- 임금·산재 중 하나를 필수 선택
- 제목, 본문, 사진 최대 3장, 선택적 사업장 입력
- 본문과 사진 중 하나 이상 입력
- K5 필수 고지 문구 노출
- 접수 성공 후 제목·본문·카테고리·접수 상태·접수 일시·사진 수를 영수증 화면에 표시

일반 사용자가 나중에 본인 제보를 다시 조회하는 API는 현재 제공하지 않습니다. 접수 성공 응답을
이용해 즉시 영수증을 보여 주고, 별도의 “내 제보 목록” 화면은 이번 범위에서 만들지 않습니다.

### 요청 2 — 감독관 목록·상세 화면 연결

- `inspector`로 로그인한 사용자만 화면에 진입
- 목록에 신고 내용 요약, 카테고리, 접수 일시, 처리 상태 표시
- 목록은 서버가 미처리 우선·동일 상태 최신순으로 반환하므로 받은 순서를 유지
- 상세에 신고 내용, 카테고리, 접수 일시, 처리 상태, 정제된 사진 표시
- 처리 상태는 표시만 하고 변경 버튼은 만들지 않음
- 관리자용 현장 제보 진입점은 만들지 않음

### 요청 3 — 개인정보 비노출 확인

화면이나 브라우저 로그에 제보자 이메일·내부 사용자 ID·원본 파일명·원본 사진 경로를 표시하거나
별도로 보관하지 말아 주세요. 사진은 API가 제공하는 인증된 감독관용 주소만 사용해 주세요.

### 요청 4 — 연동 기준

현재 K5 API는 `main`이 아니라 `task/worksite-tip-api` 브랜치에 있습니다. 연동 전 API 명세와
커밋 `197bc48`을 기준으로 확인해 주세요. 화면 구현 완료 후에는 일반 사용자 접수, 감독관 목록·상세,
일반 사용자·관리자 접근 차단을 함께 확인하면 됩니다.

### 지유 확인 완료 기준

- 일반 사용자 접수와 영수증 화면 동작
- 감독관 목록·상세·사진 조회 동작
- 두 카테고리와 세 상태의 한글 표시 확인
- 필수 고지 문구와 개인정보 비노출 확인
- 상태 변경 버튼·내 제보 목록·관리자 제보 화면을 만들지 않았는지 확인

## 6. 민서에게 요청할 사항

### 요청 1 — K5와 구현 결과 일치 여부 검수

다음 구현 결정을 K5 정보설계 기준으로 검수해 주세요.

- 카테고리 표시: 임금·산재
- 상태 표시: 접수완료·처리중·처리완료
- 최초 상태: 접수완료
- 감독관 목록: 접수완료, 처리중, 처리완료 순서이며 같은 상태에서는 최신순
- 일반 사용자는 접수 직후 영수증만 확인
- 감독관은 조회만 가능
- 관리자는 현장 제보를 조회하지 않음
- 제보자 개인정보와 원본 파일 정보는 양쪽 화면 모두 비노출

### 요청 2 — 두 고지 문구의 최종 화면 배치 확정

K5의 긴 개인정보 보호 문구는 필수로 표시하도록 구현 기준을 잡았습니다. 기존 J3의
“사진의 위치 정보는 제거되며 비공개로 접수됩니다” 문구를 별도 보조 문구로 함께 보여 줄지,
K5 문구만 보여 줄지 최종 확인 부탁드립니다.

### 요청 3 — 상태 변경 정책은 후속 범위로 기록

현재는 상태를 저장하고 표시하지만 상태를 바꾸는 주체와 흐름은 정하지 않았습니다. 감독관은
조회 전용이라는 K5 전제를 유지하여 상태 변경 API도 만들지 않았습니다. 향후 `처리중`·`처리완료`를
실제로 사용할 때 변경 주체, 변경 조건, 이력 보존 방식을 별도 정책으로 정해 주세요.

### 요청 4 — N7 뷰 불필요 판단 확인

현재 화면 요구는 원본 테이블 조회와 API 정렬만으로 충족됩니다. 별도 DB 뷰가 필요한 추가 필터·집계가
K5에 없는지 확인 부탁드립니다. 추가 요구가 없다면 나연 N7은 뷰 없이 종료할 수 있습니다.

### 민서 확인 완료 기준

- K5와 현재 API 표시 항목·비노출 항목이 일치한다는 회신
- 접수 화면에서 사용할 최종 고지 문구 배치 확정
- 상태 변경 정책을 현재 범위 밖의 후속 과업으로 두어도 된다는 확인
- 추가 필터·집계 요구가 없어 N7 조회 뷰가 불필요하다는 확인

## 7. 현재 검증 상태와 남은 일

백엔드 구현은 제품 전체 테스트 653개, DB migration drift 테스트 12개, 관련 인프라 테스트 51개와
타입 검사·프로덕션 빌드를 통과했습니다.

아직 남은 일은 다음 세 가지입니다.

1. 나연의 DB 변경 검토와 GCP DB 적용
2. 지유의 일반 사용자·감독관 화면 연동
3. 민서의 문구·상태 정책 최종 검수

실제 GCP PostgreSQL에는 `0013`을 아직 적용하지 않았습니다. 따라서 현재 상태는 “코드와 migration
준비 완료”이며, “운영 DB 전환 완료”는 아닙니다.
