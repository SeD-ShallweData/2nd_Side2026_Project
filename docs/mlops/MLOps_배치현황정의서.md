# ML 배치 현황 — 관리자 화면 정의서

* 버전 v1.1(최종) · 2026-09-11
* 근거: `docs/data-contract/self-check-spec.md`, `docs/data-contract/aggregation-spec.md`
* 대상: 임금체불 배치, 산업재해 배치 — **분모·시간 단위·등급 체계가 다르므로 화면에서 항상 분리 표시, 합산 금지**

\---

## 1\. 배치 기준일(as\_of)과 예측 대상 월(target\_month)

**뜻**: as\_of는 이번 배치가 어느 시점까지의 관측 데이터를 썼는지, target\_month는 그 데이터로 몇 월(임금체불) 또는 몇 주(산업재해)를 예측했는지. 임금체불은 as\_of\_date=2026-06-01 → target\_month=2026-12-01(6개월 지평, DB가 as\_of+6개월로 자동 계산). 산업재해는 prediction\_as\_of=2026-04-19 → target\_week=2026-04-20\~26로, **전 행이 `stale\_target\_week` 상태**(예측 대상 시점이 이미 지남)다.

**관리자가 왜 봐야 하나**: 낡은 예측을 최신처럼 노출하는 사고를 막는 최소 확인선이다. 산업재해는 지금 구조상 항상 지난 시점을 예측하므로, "지남" 상태 자체를 화면에 노출해야 한다.

**어디서 가져오나**: `manifest.json`의 `as\_of` 필드. self-check-spec.md M2 — `YYYY-MM` **형식**은 검사 가능하지만, 그 값이 실제 관측창 종료월과 일치하는지는 **파일만으로 검사 불가**(⚪). 화면에 이 한계를 그대로 노출한다.

\---

## 2\. 적재 행수

**뜻**: 이번 배치로 DB에 들어간 사업장 수. 임금체불·산업재해 각각 별도로 센다.

**관리자가 왜 봐야 하나**: 갑자기 줄면 파이프라인 데이터 유실 신호이며, 3번(등급 분포) %를 왜곡시키는 선행 지표다.

**어디서 가져오나**: aggregation-spec.md §1.1 — 임금체불 **553,598**(`v\_current\_scored`, 채점 대상 전체. 판정 있음 서브셋 503,887을 쓰면 판정 없는 49,711곳이 집계에서만 사라져 개별 조회 화면과 어긋난다). 산업재해 **515,608**(`industrial\_safety.v\_llm\_firm\_safety\_context`). 1차 검증은 self-check-spec.md M3(manifest 기대 행수 vs 실제 행수 일치).

## 3\. 등급 분포 (4종 — 원 요청 3종에서 정정)

**뜻**: 임금체불은 normal/watch/**review**/unknown 4종, 산업재해는 상위1%/상위5%/상위10%/일반 4종 밴드. review를 빼면 합이 95.61%가 되고 업종 순위가 뒤집힌다(watch 기준 건설업 76.9%→하위권, review 기준 12.3%→1위).

**관리자가 왜 봐야 하나**: 비율이 지난 배치와 크게 다르면 모델·파이프라인 이상 신호. review는 모델 예측이 아니라 **공표된 사실**이라 가장 중요하다. 산업재해 밴드는 **전국 전체 기준**이라 지역·업종 필터를 걸어도 재계산되지 않는다는 점을 관리자가 인지해야 한다.

**어디서 가져오나**: aggregation-spec.md §2 — normal 5.89%("뚜렷한 이상 신호 없음"), watch 77.97%("안전 신호 미확인", **회색만·노랑주황빨강 금지**), unknown 12.15%("분석 자료 부족", **초록·긍정 아이콘 금지**), review 3.99%("우선 확인 필요"). §8.3 — 상위1% 1.00%, 상위5% 4.02%(1\~5% 구간), 상위10% 4.98%(5\~10% 구간), 일반 89.99%.

## 4\. 드리프트 검사 결과

**뜻**: self-check-spec.md의 **25개 항목**(F1-3·C1-3·V1-10·R1-4·M0-3)으로 "구조가 계약대로인가"를 보는 **스키마 드리프트** 검사. ML의 **데이터 드리프트**(분포 변화, 3번 항목 개념)와는 다르다.

**관리자가 왜 봐야 하나**: 스키마가 깨지면 이후 계산 전체가 무의미해지므로 가장 먼저 봐야 한다.

**어디서 가져오나**: 종료 코드 0="정상", 1="불일치". **🟡 경고(6항목)·⚪ 검사 불가(5항목)는 종료 코드에 안 잡히므로 "정상" 배지 옆에 항상 "경고 N건·검사 불가 N건"을 같이 표기**한다 — "⚪를 ✅로 세지 않는다"는 원문 원칙을 화면 구조로 강제.

\---

## 5\. 유효기간(valid\_until) 🔶 출처 미확인 — 확정된 것처럼 쓰지 않는다

**뜻**: 지금 결과를 언제까지 믿어도 되는지, 다음 배치 예정일.

**관리자가 왜 봐야 하나**: 지났는데 안 바뀌면 파이프라인 중단 신호다.

**어디서 가져오나**: 🔶 두 문서 어디에도 "다음 배치 예정일" 저장 필드가 없다. 승석·민규 확인 전까지는 **API 응답에 이 필드가 없을 가능성을 전제로 구현**해야 한다(null 허용, "갱신 확인 필요" 폴백 필수).

\---

## 6\. 확인 필요한 항목

1. valid\_until을 저장하는 테이블/필드 실존 여부, 없으면 신설 위치
2. 드리프트 검사기 실행 결과를 관리자 화면 API가 조회하는 방식(실시간 실행 vs 저장된 로그 테이블)
3. 화면 스타일 체계 — Tailwind인지 CSS 변수(CDS류) 기반인지 (아래 코드는 Tailwind로 통일)
